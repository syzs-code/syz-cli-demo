# SYZYGY — CLI & Format Manual

The full reference: every command, flag, file format, directory structure, resolver expression, and assertion operator. For the mental model and best-practice guidance see `SYZ-GUIDELINES.md`; for the test-authoring workflow see `SYZ-TESTING.md`.

## Writing scenarios

### Regular scenario

```yaml
name: "Checkout — successful order"
level: e2e
plugins:
  - name: payments
    version: "1.0.0"

flow:
  - type: send
    procedure: payments.send_order
    inputs: {}   # all inputs defaulted from manifest.defaults

  - type: validate
    procedure: payments.validate_order_response
    inputs:
      response:        "{{ ledger.payments.send_order.http.response }}"
      expected_status: 201

  - type: workflow
    procedure: payments.workflow_checkout

  - type: workflow
    procedure: payments.workflow_checkout
    overrides:
      - step: payments.send_order
        inputs:
          body:
            amount:   10000
            currency: "USD"
      - step: payments.validate_order_response
        inputs:
          expected_status: 400

  # Craft step — renders a local artifact (no network call)
  - type: craft
    procedure: mq.craft_order_message
    inputs:
      orderId:  "{{ ledger.payments.send_order.outputs.orderId }}"
      amount:   100
      currency: "GBP"

  # Downstream send step using the crafted file path (requires output_to_file on manifest)
  - type: send
    procedure: mq.send_publish_message
    inputs:
      topic:        "order.created"
      message_file: "{{ ledger.mq.craft_order_message.outputs.filePath }}"

  # Alternative: reference the rendered content directly (always available regardless of output_to_file)
  - type: send
    procedure: mq.send_publish_message
    inputs:
      topic:   "order.created"
      message: "{{ ledger.mq.craft_order_message.response.body }}"
```

**`level`** is a free-form string. Common conventions: `component`, `integration`, `e2e`, `uat` — matching the folders under `.syz/scenarios/`. SYZYGY does not enforce specific values.

**`plugins`** lists plugins this scenario consumes, with versions. Used by `syz lint` to verify required plugins are installed. Required field.

### Named connections — `connections` handles + the `connection` field

Every executor — stateful or stateless — carries its connection-defining identity (base URL, brokers, host, credentials) in a **named connection handle**, so those details live in **one** place rather than being repeated on every step. Stateful executors (a message-broker producer, a database session, an SFTP connection) can additionally hold a connection open across steps; stateless executors (like `http`) connect and disconnect within each step.

A handle is a named block carrying the executor's `execution_library`, an optional **`lifecycle`**, and — **wrapping** the executor block — the identity. For every executor the wrapped block is `<execution_library>: { request, settings }` (the same structured shape a send procedure authors; see *HTTP requests* below). It can be declared in places that compose by a single precedence (see below):

```yaml
# environment file (.syz/environments/local.yaml) — or inline in the scenario
connections:
  payments_api:
    execution_library: http
    lifecycle: ephemeral           # keep_alive | ephemeral (default: ephemeral)
    http:                          # the wrapped executor block
      request:
        fields:  { base_url: "https://api.payments.local" }
        headers: { Authorization: "{{ os-env-var:PAYMENTS_TOKEN }}" }   # masked
      settings: { timeout_ms: 10000 }
```

A `send` step references a handle by name with the optional **`connection`** field:

```yaml
flow:
  - type: send
    procedure: payments.create_order
    connection: payments_api       # identity comes from the handle
    inputs:
      order: { amount: 100 }       # only per-call data here
```

#### Connection precedence — one rule, deep-merged

The effective executor block is composed field-by-field under a **single** nearest-wins rule. Higher layers win per field; objects merge sub-key by sub-key:

```
env  <  procedure  <  scenario  <  step          (step > scenario > procedure > env)
```

Concretely the layers, lowest to highest, are: **env `connections.<name>`** < **procedure `connection`** (base identity) < **procedure `http`** (the operation) < **scenario `connections.<name>`** < **step `connection_overrides`**.

- **env `connections`** (lowest) — the deployer's location/tuning for the environment.
- **procedure `connection`** beats env — **identity authority is the plugin's** (`procedure > env`, inverting older guidance). For a deployer to override a plugin's identity through env, the procedure must ship that identity as a **`{{ env.* }}` / `{{ os-env-var:* }}` reference**, not a literal (a literal location field on a procedure-layer block raises the `LITERAL_IDENTITY_IN_PROCEDURE_BLOCK` **warning**). The procedure block is **secret-free by contract**: only `{{ os-env-var:NAME }}` / `{{ env.x.y }}` references and non-secret literals — a literal secret is `LITERAL_CREDENTIAL_IN_CONNECTION`.
- **procedure `http`** (the operation block — method/path/body) merges over the procedure's connection identity.
- **scenario `connections`** beats the procedure — a scenario can retarget for its run.
- **step `connection_overrides`** (highest) — a per-step negative-test lever. It wraps the executor block (`{ http: { request, settings } }`), can tune any field, but **cannot change `execution_library`** (`CONNECTION_OVERRIDE_EXECUTION_LIBRARY`). A **`null`** value is the **unset/remove-this-field** sentinel — e.g. drop `Authorization` to assert a 401:

```yaml
    connection_overrides: { http: { request: { headers: { Authorization: null } } } }
```

#### Connection negatives are data, not failures

A send **never** fails on a connection problem. Every connection negative — connect-time (bad credentials, dead host, TLS error) **and** post-open (HTTP 403, SQL constraint violation, native error code) — is captured as response **data**, the step's outcome stays absent, and the run continues. A completed exchange (including a 4xx/5xx) lands in `$.fields`; a transport negative that never completed lands in `$.error`. A `validate` step decides whether that was acceptable. There is no connect-time exception and no framework "verify the connection" field. To assert a connection works, author a **workflow**: a `send` followed by a `validate` asserting `$.error` `not_exists`.

#### keep_alive failed-open — dead handle, no retry

If a `keep_alive` handle fails to open on first reference, the native connect error is captured as that step's `body.error` and the handle is marked **dead** — it is *not* retried. Any later step naming the same handle emits `body.error.code: NO_LIVE_CONNECTION` (carrying `connection`, `established_at_step`, `duration_ms: 0`) **without** attempting to reconnect; teardown skips dead markers. This applies to `keep_alive` only — `ephemeral` handles open fresh per step, so a later step gets a fresh attempt.

Rules:

- **Stateful steps require a handle.** A step whose procedure uses a stateful executor with no `connection` is an error (`MISSING_CONNECTION`).
- **A `connection` on a stateless executor is allowed.** It just supplies identity; the step is still ephemeral. (There is no longer a `CONNECTION_ON_STATELESS_EXECUTOR` error.)
- **Handle must resolve.** A `connection` naming a handle that neither a `connections` block (env or scenario) **nor** the procedure's own connection block declares is an error (`UNKNOWN_CONNECTION`).
- **Executor must match.** A handle's `execution_library` must match the procedure's (`CONNECTION_EXECUTOR_MISMATCH`). A handle is bound to one executor for its life.
- **`keep_alive` is for stateful executors only.** A `keep_alive` lifecycle on a stateless executor is an error (`KEEP_ALIVE_ON_STATELESS_EXECUTOR`).
- **No literal secrets in connection blocks.** A secret-named field (password, token, api_key, secret, …) carrying a literal value in any committed connection block — procedure block or scenario `connections` — is an error (`LITERAL_CREDENTIAL_IN_CONNECTION`). Route it through `{{ os-env-var:NAME }}`. The scan recurses into nested objects, so a secret nested under a container (e.g. an `http` bearer at `auth.token`) is caught at its secret-named leaf — the reported field is the dotted path (`auth.token`).
- **`connection_overrides` can't retarget.** Setting `execution_library` under `connection_overrides` is an error (`CONNECTION_OVERRIDE_EXECUTION_LIBRARY`).
- **Transactions need `keep_alive`.** A transactional operation (`begin`, `commit`, `rollback`, `abort`, `exec`, `discard` in step `inputs.operation`) requires the handle's lifecycle to be `keep_alive` (`TRANSACTION_REQUIRES_KEEP_ALIVE`).
- **Unknown fields warn.** A handle field outside the executor's known connection fields is a lint **warning** (`UNKNOWN_CONNECTION_FIELD`).
- **Lifecycle.** `keep_alive` opens lazily on first reference and is reused across steps; `ephemeral` (the default when `lifecycle` is omitted) opens and closes within each step.
- **Scenario-scoped.** Every live connection is closed at the end of the scenario (even if a step fails mid-flow). Handles never carry across scenarios — each scenario starts fresh.

**`http` connection identity.** An `http` handle wraps an `http: { request, settings }` block (see *HTTP requests* below). Typically the handle carries the location (`request.fields.base_url`) and shared headers (`request.headers.Authorization`); the procedure's own `http` block carries **both the base identity and the operation** (`method`, `path`, `body`) — `syz generate` folds them into that one block. The handle's only top-level identity key is `http` — a flat field (e.g. `base_url` at the handle root) is unknown and raises the `UNKNOWN_CONNECTION_FIELD` warning.

**Named handle vs `{{ env.* }}` reference.** Two paths reach env-backed identity: a **named handle** (`connections.<name>`, consumed by `connection:`) and a plain **`{{ env.<plugin>.<procedure>.<field> }}` reference** inside the procedure's own block. Ship a **named handle** when identity is shared across procedures/steps, must be reused or renamed, or the executor is **stateful** (where `connection:` is required). Use **plain references** for single-procedure identity (what `syz generate` emits by default). Both resolve through the same env file.

#### Provenance — the `debug.log` blame view

To see exactly which layer set each connection field, read `debug.log` (`syz run --debug` or the per-step debug artifact). The `[Payload Construction]` section prints a `Connection:` blame view — for each field, the winning layer, any `[shadowed: …]` layers it overrode, and `via {{ os-env-var:NAME }}  [MASKED]` for secret-sourced values. Provenance is debug-log only and never reveals a masked secret.

### Executor tuning defaults — env `executors`

Per-executor **behaviour/tuning** lives in the `settings` half of the `http` block, layered by the same precedence as everything else. For an **environment-wide default** there is one extra container: the reserved env-root **`executors:`** block, keyed by `execution_library`, carrying a `settings` map. It only ever **gap-fills** a `settings` field the merged block left unset — *if provided, set it; else leave it.*

```yaml
# environment file (.syz/environments/local.yaml) — broadest tuning default
executors:
  http:
    settings:
      timeout_ms: 5000          # applied to every http send that doesn't set it
      tls: { verify: true }
```

To tune a single scenario or step, set the field in that layer's `http.settings` (via a `connections` handle or `connection_overrides`) — it wins over the env `executors` default by precedence.

- **Lowest precedence.** `executors` gap-fills only what the layered `http.settings` left unset; any nearer `settings` value wins.
- **Deep merge, field-by-field.** Nested objects (e.g. `tls: { verify, ca_cert }`) compose key-by-key.
- **Allowlist only — no injection.** Only an executor's *config fields* (its `settings` keys) may be gap-filled. A non-`settings` sub-key (e.g. `executors.http.request`) is **structurally ignored** — identity and `request.body` are never injectable. Identity belongs in a `connections` handle; per-call data stays in the step.
- **`null` is honoured.** A field explicitly nulled by `connection_overrides` is **not** silently re-filled by the env `executors` default.
- **Audited.** The effective merged payload is what runs and what `ledger.json` records; `debug.log`'s `[Input Resolution]` tags each gap-filled field `(executors)`.
- **Lint.** An unknown `settings` key, a non-`settings` sub-key, or an unknown `<type>` in `executors` is a **warning** (`UNKNOWN_EXECUTOR_CONFIG_FIELD`).

**`http` settings (the config fields):** `timeout_ms`, `follow_redirects`, `max_redirects`, `tls`, `proxy`, `query_array_format`, `max_capture_bytes`.

### Scenario outline (parameterised runs)

Each row in `examples` is one fully isolated execution. The flow references row values via `{{ outline.x }}`. Example values may themselves contain `{{ }}` references.

```yaml
name: "Checkout — parameterized amounts"
level: e2e
plugins:
  - name: payments
    version: "1.0.0"

flow:
  - type: send
    procedure: payments.send_order
    inputs:
      userId:   "{{ outline.userId }}"
      amount:   "{{ outline.amount }}"
      currency: "{{ outline.currency }}"

  - type: validate
    procedure: payments.validate_order_response
    inputs:
      response:        "{{ ledger.payments.send_order.http.response }}"
      expected_status: "{{ outline.expected_status }}"

examples:
  - name: standard-order
    userId:          "{{ env.payments.test_user_id }}"
    amount:          100
    currency:        "GBP"
    expected_status: 201

  - name: zero-amount-rejected
    userId:          "{{ env.payments.test_user_id }}"
    amount:          0
    currency:        "GBP"
    expected_status: 400

  - name: ai-generated-amount
    userId:          "{{ env.payments.test_user_id }}"
    amount:          "{{ ai: generate a random valid order amount between 1 and 9999 }}"
    currency:        "GBP"
    expected_status: 201
```

The presence of the `examples` field (not a `type` flag) is what makes a file a scenario outline. Each example produces a separate results folder: `.syz/results/<run-id>/e2e/checkout-parameterized/standard-order/`.

### Selecting a subset — tags, suite manifests, `--tag` / `--example`

By default `syz run --suite <path>` executes **every** scenario and **every** outline row a file or directory contains. Three composable selectors let you run a subset; all three work identically on `syz run` **and** `syz lint` (lint previews exactly the rows a run would execute, without running them). A non-outline scenario is treated as a single **row**; an outline contributes one row per example.

**Tags.** Add an optional `tags` field on a scenario and/or on each `examples` row. It accepts a YAML list **or** a comma-separated string — `tags: [smoke, critical]` ≡ `tags: "smoke, critical"` (split on commas, trimmed, empties dropped, de-duped, **case-sensitive**). A row's **effective tags** are the scenario-level tags ∪ that row's tags — so a scenario tag labels every row, and a row tag refines one.

```yaml
name: "Checkout"
level: e2e
tags: [smoke, payments]          # labels every row in this file
plugins:
  - name: payments
    version: "1.0.0"
flow:
  - type: send
    procedure: payments.send_order
    inputs: { amount: "{{ outline.amount }}" }
  - type: validate
    procedure: payments.validate_order_response
    inputs: { response: "{{ ledger.payments.send_order.http.response }}" }
examples:
  - name: standard
    amount: 100
  - name: edge-zero
    amount: 0
    tags: [edge]                 # effective tags here = smoke, payments, edge
```

`tags` is a **reserved row key**: it is stripped from the `{{ outline.* }}` data namespace, so `{{ outline.tags }}` never resolves. `{{ outline.name }}` still resolves as before.

`syz generate` emits `tags` in this **flow form** (`tags: [sample, smoke]`), matching the canonical authoring form shown above — both forms parse identically.

Run only the matching rows with `--tag` (single flag, comma-list, **OR-union** — a row is kept if its effective tags intersect the requested set; a row with no tags never matches a non-empty `--tag`):

```bash
syz run  --suite .syz/scenarios --env local --tag smoke
syz lint --env local --tag smoke,critical          # preview the same set, no run
```

**Suite manifests — curated playlists.** A manifest is a YAML file with a top-level `scenarios:` array (and **no** `flow:` key — that structural shape is what marks it a manifest; the `.suite.yaml` extension is a convention, not a requirement). Convention: keep them in `.syz/suites/<name>.suite.yaml`. Entries are paths **resolved under `.syz/scenarios/`** (a workspace-relative `.syz/scenarios/...` form is also accepted):

```yaml
# .syz/suites/release.suite.yaml
name: Release gate          # optional, display-only label
scenarios:
  - e2e/checkout.yaml       # a file entry → that one scenario
  - integration/           # a folder entry → every .yaml under it, recursively
  - e2e/refund.yaml
```

Listed order is preserved; duplicates are dropped **first-occurrence-wins**; an empty folder entry warns and continues; a missing path entry fails fast naming the entry; `scenarios: []` is a schema error. Pass it as `--suite`:

```bash
syz run --suite .syz/suites/release.suite.yaml --env local
```

**Outline `--example`.** Select outline rows by their resolved example name — the explicit `name:`, else `example-<i>` (1-based) — the same value written to `execution.json`. Single flag, comma-list, OR-union. Because it is meaningful only for outlines, **plain scenarios are excluded** whenever `--example` is present. A name need only exist in one in-scope outline; the same name in two outlines selects both rows.

```bash
syz run --suite .syz/scenarios/e2e/checkout-param.yaml --env local --example edge-zero,standard
```

**Composition.** `--tag` and `--example` intersect (each narrows; filters never add). An unknown example name raises `UNKNOWN_EXAMPLE` (listing the available names); `--example` against a set with no outlines raises `EXAMPLE_SELECTOR_ON_NON_OUTLINE`; selectors that empty a non-empty discovery raise `NO_SCENARIOS_MATCH_SELECTOR`; an empty discovery raises `NO_SCENARIOS_FOUND`. `execution.json` records the active selection (`suite`, `tags`, `examples`, `matched`, `skipped`).

### Requirement coverage — `covers:`

`covers:` links a test to the requirement ids (`REQ-<SCOPE>-<PG|DOM>-<NNN>`, defined in `PLUGIN-GUIDE.yaml` / `DOMAIN.yaml`) it discharges. It is **distinct from `tags:`** — tags are the *slicing* vocabulary (`--tag`), `covers:` is *requirement linkage* (`syz rtm`). Same string-or-list form as tags (`covers: REQ-PAY-PG-001` ≡ `covers: [REQ-PAY-PG-001, REQ-PAY-PG-002]`).

**Allowed loci** (many-to-many — one test may cover several requirements; one requirement may be covered by several tests):

- **scenario** — top-level `covers:` on the scenario file.
- **outline example row** — a `covers:` key on an `examples:` row (a **reserved row key**, like `tags` — stripped from `{{ outline.* }}`, so `{{ outline.covers }}` never resolves).
- **flow step** — `covers:` on any `send` / `validate` / `workflow` / `craft` step.

The effective coverage of a row is the union `scenario ∪ row ∪ step`. **`covers:` is never allowed on a procedure** (`COVERS_ON_PROCEDURE` lint error) — a procedure is a reusable definition shared across scenarios, so coverage there is ambiguous. Targets are owned-plugin PG ids + DOM ids only; a `covers:` pointing at no such requirement (or at an installed-plugin requirement) is `DANGLING_COVERS_REF`.

```yaml
name: pay-boundaries
level: component
plugins: [{ name: payments, version: "1.0.0" }]
covers: REQ-PAYMENTS-PG-001            # scenario-level
flow:
  - type: send
    procedure: payments.create_payment
    inputs: { amount: "{{ outline.amount }}" }
  - type: validate
    procedure: payments.validate_created
    inputs: { response: "{{ ledger.payments.create_payment.http.response }}" }
    covers: REQ-PAYMENTS-PG-002          # step-level
examples:
  - { name: over-max, amount: 1000001, covers: REQ-PAYMENTS-PG-003 }   # row-level
```

Report coverage with `syz rtm` (below). `syz lint` warns on any uncovered in-scope requirement (`UNCOVERED_REQUIREMENT`, scope = owned-PG + DOM).

### Defaults/overrides precedence

There are two distinct merge layers applied for every step.

**Layer 1 — Workflow overrides (shallow field-level merge):**

When a scenario runs a `workflow` step with `overrides`, only the keys explicitly listed in `overrides[].inputs` replace the workflow's wiring for that step:

```
final = { ...workflow.step.inputs, ...override.inputs }
```

Unmentioned keys keep the workflow's original wiring.

**Layer 2 — Step input resolution (deep merge):**

Applied to every step after Layer 1:

```
resolved = deepMerge(manifest.defaults, step.resolved_inputs)
```

`manifest.defaults` are resolved first, then deep-merged with the step's resolved inputs. Scenario inputs win on conflict. Objects merge recursively. Arrays replace wholesale. Outline values flow through `{{ outline.x }}` references in either layer.

### Context variables — `{{ ctx.var.* }}`

A scenario-scoped, **mutable** key-value namespace any step writes via a `set:` block and any later step reads via `{{ ctx.var.<name> }}`. The map is reset per scenario **and** per outline example row, and is **never** written to `ledger.json` or any on-disk artifact. Use it when a value's **source location is unknown or awkward at authoring time, or it is shared across steps/plugins** — the canonical case being a resource `id` captured from one step and threaded into a later URL **path**. When the producing procedure and response path are known and local, prefer a direct `{{ ledger.<procedure>… }}` reference.

**Write** with a `set:` block — available on every leaf step (`send`/`validate`/`craft`, including leaf steps inside a workflow procedure). It resolves **after** the step executes but **before** its ledger entry is committed, against a transient snapshot seeded with the step's own fresh output (so `{{ ledger.<this-step>… }}` is referenceable in `set:`). For setting many vars in one place with no send/validate attached, use the reserved built-in craft procedure **`syz.set_context_var`**.

```yaml
flow:
  # Capture from a send's own response.
  - type: send
    procedure: orders.create_order
    set:
      order_id: "{{ ledger.orders.create_order.http.response.fields.body.id }}"

  # Read anywhere later — origin-agnostic. Here, threaded into a URL path variable.
  - type: send
    procedure: orders.get_order            # procedure path: /orders/{{ ctx.var.order_id }}/items

  # Standalone setter — many vars in one place.
  - type: craft
    procedure: syz.set_context_var
    set:
      tenant: "acme"
      region: "{{ env.orders.region }}"
```

**Read** with `{{ ctx.var.<name> }}`, anywhere a `{{ }}` reference is valid. Reads are **temporal** (the writing `set:` must have run earlier in the same scenario). Reading an unset key is a hard error: runtime throws `UnsetContextVarError`; `syz lint` throws `UNKNOWN_CONTEXT_VAR` (a `ctx.var.*` read whose key is set nowhere in the resolved flow — including procedure-shipped `set:` blocks).

**Mask** a captured secret by listing the `ctx.var.<key>` in the step's `sensitive_fields` (now accepted at the **step** level, namespace-routed by each entry's head segment):
- `ctx.var.<key>` → masked **by location** (length-independent): its ctx-panel entry is blanked, and every later step that injects `{{ ctx.var.<key> }}` into a field has that destination path blanked in the recorded request — while the **live value still flows** into the real request. If the value is also `>= 5` chars it is additionally registered into the run value-net as defence-in-depth. (M44F.)
- `response.*` / `request.*` / `<executorKey>.*` → the existing **path-based** in-place mask.

```yaml
  - type: send
    procedure: auth.login
    set:
      auth_token: "{{ ledger.auth.login.http.response.fields.body.token }}"
    sensitive_fields:
      - response.body.token            # path-mask the login response in the ledger
      - ctx.var.auth_token             # masked by location (panel + injection paths), live value preserved
```

Masking happens **before** the capturing step's ledger commit, so the originating response cannot leak the raw secret; for a sensitive `ctx.var` captured from a response, the source field is blanked by location too. A sensitive `ctx.var` resolving to a very short literal still raises the non-blocking `WEAK_SENSITIVE_CONTEXT_VAR` warning — such a value is masked by location but sits below the value-net length floor, so if a server **echoes** it into an **undeclared** field it is not caught; declare that field to cover the residual.

**Reserved namespace.** `ctx` is a reserved prefix (cannot be a plugin name); only `ctx.var.*` is author-writable — the rest of `ctx.*` is reserved for future read-only scopes. The entire `syz` prefix (`/^syz/i`, any separator) is reserved framework-wide across plugin / procedure / connection-handle / ctx-var / env-key names — using it raises `RESERVED_SYZ_IDENTIFIER` (`syz.set_context_var` and the `SYZ-` dossier files are framework-owned exceptions).

The report shows a per-step before/after **Context Variables** panel (masked); `debug.log` carries a matching `[Context Variables]` block. Nothing ctx-related is written to `ledger.json`.

### Fixed delay — `syz.wait`

A reserved built-in **craft** procedure that pauses the flow for a fixed number of milliseconds. Like `syz.set_context_var` it has no plugin, template, or crafter — it is always available and is framework-owned (exempt from the `/^syz/i` reservation and from plugin/procedure-file existence checks). Its **sole input** is `ms` — a **non-negative number** (`0` is allowed; `{{ }}` references that resolve to a number are accepted). It is repeatable any number of times in a flow.

```yaml
flow:
  - type: craft
    procedure: syz.wait
    inputs:
      ms: 58000          # pause ~58s — a literal, or a numeric {{ }} reference
```

The step is recorded as a **normal craft step** in the trace, `ledger.json`, and the report — `type: craft`, carrying its real `duration_ms`. It **never judges**: a completed wait is `success` and the scenario continues; like any craft it halts only on `error`/`exception` (a scenario may legitimately end on a `syz.wait` — a craft is not a send, so the send-ends-a-scenario → `aborted` rule does not apply). `syz lint` validates that `inputs.ms` is a non-negative number (a literal negative / non-number is a lint **error**); a bad value that only appears after `{{ }}` resolution faults the step at run time with `INVALID_WAIT_MS` (outcome `error`).

A **fixed** wait is a flakiness smell — see SYZ-GUIDELINES. Reserve it for genuinely fixed windows (a rate-limit window, a TTL expiry, a job scheduled at +N seconds). To wait **until the system reaches a state**, prefer a polled workflow (`poll:`) over guessing a duration.

### Poll until converged — `poll:` on a workflow step

An optional `poll:` block on a **workflow** flow-step re-runs the referenced workflow until its **worst-wins aggregate outcome** is `success`, or a bound trips. This is the primitive for **eventual consistency** — asserting a state that becomes true some unknown time after a write (an async consumer caught up, a row materialised, an object appeared).

```yaml
flow:
  - type: workflow
    procedure: payments.settle_order_send_success
    poll:
      max_attempts: 10     # required — the finite bound (integer >= 1)
      interval_ms: 2000     # optional base delay between attempts (default 0)
      backoff_ms: 1000      # optional LINEAR increment per attempt; unset → fixed interval
      timeout_ms: 60000     # optional secondary wall-clock cap
```

- **Valid only on a workflow step** — never on `send`/`validate`/`craft`. Placing `poll:` elsewhere is a lint error (`POLL_ON_NON_WORKFLOW_STEP`).
- The poll condition is the workflow's aggregate outcome: `success` → **done (early-exit)**; `failure` → **retry**; `error`/`exception`/`aborted` → **break out and halt immediately** on the attempt it occurred. **Only `failure` retries** — a fault is never retried (retrying a broken setup buries the cause).
- Intermediate `failure`s are **recorded but not terminal** (the validate stop-rule is suppressed mid-loop). **Exhaustion** — `max_attempts` reached or `timeout_ms` elapsed with no passing attempt — surfaces as the **last attempt's `failure`**, which re-enters the normal stop path (`syz run --continue-scenario-on-failure` applies). There is **no new error code**.
- Inter-attempt delay between attempt *n* and *n+1* is `interval_ms + (n−1)×backoff_ms` (linear); `timeout_ms` is checked between attempts.
- Each attempt re-runs the workflow's sends, so the ledger gains `<procedure>`, `<procedure>[1]`, `<procedure>[2]`… (one per attempt). A **bare** `{{ ledger.<procedure>… }}` reference resolves to the **latest** write (see *Ledger references* below), so the workflow's per-attempt `validate` reads **that attempt's** fresh send.
- The report and `debug.log` render the polled workflow as one row with each attempt nested beneath it (the trace carries an `attempts[]` array); `totalSteps` counts the workflow once, regardless of attempt count.
- A polled workflow with **no validate sub-step** has nothing to converge on — a lint **warning** (`POLL_WITHOUT_VALIDATE`).

## Assertions

All assertions live inside validate procedure `checks` arrays.

### The response envelope — `fields`, `headers`, `error`

A **send** step records a structured response at `<procedure>.http.response` (mirroring the `http.request` block). A validate step receives it via `response: "{{ ledger.<procedure>.http.response }}"`, and assertion `path`s and `{{ ledger }}` references target three roots **within that response object**:

| Root | Holds | Example path |
|---|---|---|
| `$.fields` | Native facts on a completed exchange: `status_code`, `reason_phrase`, `http_version`, and `body` (the payload, decoded per Content-Type) | `$.fields.status_code`, `$.fields.body.orderId` |
| `$.headers` | Observed response headers (case-insensitive). `Set-Cookie` is auto-masked | `$.headers.content-type` |
| `$.error` | A **transport negative** captured as data — `{ code, message }` carrying the executor's native code. Present **only** when the call could not complete (connection refused, DNS failure, TLS error, timeout); when present, `fields`/`headers` are absent | `$.error.code` |

A send **never decides pass or fail itself.** An HTTP 4xx/5xx is a *completed* exchange: its body lands in `$.fields.body` and its status in `$.fields.status_code` — assert on those. Only a failure to complete the call at all (no response received) produces `$.error`. The verdict is always a downstream `validate` step's job. Use `type: http` for `$.fields.*` / `$.headers.*`; use `type: json` for everything under `$.fields.body`; assert transport negatives at `$.error`.

> A response body larger than `settings.max_capture_bytes` (default ~5 MB) is truncated in the ledger with a `truncated: true` marker — never silently lost.
>
> A **craft** step is different: it keeps a top-level `response` with the rendered artifact at `response.body` (referenced as `{{ ledger.<plugin>.<craft>.response.body }}`) and an optional `response.metadata.output_file_path`. Only `send` steps use the `http.response` envelope above.

### Step outcomes — the unified vocabulary

Every step records an `outcome`, and the scenario rolls them up (worst wins):

| Outcome | Meaning | Stops the scenario? |
|---|---|---|
| `success` | The step did its job (send completed, all checks passed) | No |
| `failure` | A `validate` step had at least one failed check | Yes¹ |
| `error` | An authoring/recoverable fault (bad template, unresolved input, unknown executor) on a `craft` or `validate` step | Yes |
| `exception` | An environment-side fault (AI provider down, file write failed) | Yes |
| `aborted` | A syz-internal fault, or a `send` step that threw before completing | Yes |

A normal `send` carries **no** success/failure/error of its own — its outcome is absent (rendered as `success` in reports). The only outcome a send can raise is `aborted`.

¹ `syz run --continue-scenario-on-failure` exempts the `failure` case only: a failed `validate` records its verdict and the flow continues to the next step, so one run surfaces every failed check. `error`/`exception`/`aborted` still halt unconditionally. The verdict is unchanged — the scenario still rolls up worst-wins (a `failure` keeps it `failure`).

Aggregation order: `aborted > exception > error > failure > success`. A scenario is `success` only when every `craft`/`validate` step is `success` **and** the flow does not end on a `send` step — a flow that ends on a send asserts nothing, so it is reported `aborted` (and `syz lint` warns with `TERMINAL_SEND_STEP`). Always follow a final send with a validate.

### `http` — HTTP response status / headers / version

```yaml
- type: http
  path: "$.fields.status_code"
  operator: equals
  value: 201

- type: http
  path: "$.headers.content-type"
  operator: contains
  value: "application/json"

- type: http
  path: "$.fields.http_version"
  operator: equals
  value: "1.1"
```

### `json` — JSONPath assertions on JSON body

```yaml
- type: json
  path: "$.fields.body.orderId"
  operator: exists

- type: json
  path: "$.fields.body.amount"
  operator: greater_than
  value: 0

- type: json
  path: "$.fields.body.status"
  operator: in
  value: ["confirmed", "pending", "processing"]

- type: json
  path: "$.fields.body.items[*].quantity"
  operator: all
  checks:
    - type: json
      operator: greater_than
      value: 0

- type: json
  path: "$.fields.body.items"
  operator: count_equals
  value: 3

- type: json
  operator: expression
  expression: "response.fields.body.total === response.fields.body.subtotal + response.fields.body.tax"

- type: json
  description: "Response body matches the order schema"
  path: "$.fields.body"
  operator: matches_schema
  value:
    type: object
    required: [orderId, amount, currency]
    properties:
      orderId:  { type: string }
      amount:   { type: number }
      currency: { type: string }
      items:
        type: array
        items:
          type: object
          required: [sku, qty]
          properties:
            sku: { type: string }
            qty: { type: number }
```

**`matches_schema` supported keywords:** `type` (`string` | `number` | `boolean` | `object` | `array` | `null`), `required`, `properties`, `items`. This is a deliberate subset of JSON Schema — no `$ref`, `oneOf`, `pattern`, `enum`, etc. The check stops at the first violation and reports its path in the result's `detail` field (e.g. `"items[2].qty: expected type number, got string"`).

**`expression` execution:** runs in a sandboxed `node:vm` context with `response` (the full response envelope: `body`, `content_type`, `format`, `metadata`) and `inputs` (the step's resolved inputs) in scope. Standard JS — `===`, `&&`, `||`, ternary, arithmetic, array methods are all available. Must return a boolean (a non-boolean result fails the check). 1-second execution timeout.

### `text` — string assertions on text body

```yaml
# content is an input key — resolvedInputs[content] = the text to validate.
# When content is absent the full response body is used (backward-compatible default).

- type: text
  content: RESPONSE_BODY       # input key → resolvedInputs[RESPONSE_BODY]
  operator: contains
  value: "success"

- type: text
  content: RESPONSE_BODY
  operator: matches
  value: "^order-[0-9]{6}$"

# No content field — validates full response body directly:
- type: text
  operator: contains
  value: "success"
```

### `ai` operator — AI-evaluated assertions

Use `operator: ai` on any assertion type (`http`, `json`, `text`). The value shown to the AI is: the JSONPath result (`json`/`http`), or the text from `content` / full response body (`text`). Provide the rule in `instruction`.

```yaml
- type: json
  description: "Batch routing follows time-based rules"
  path: "$.fields.body.batchId"
  operator: ai
  instruction: "The value must be A between 08:00-13:00 UTC, B between 13:00-17:00, otherwise C"

- type: http
  path: "$.fields.status_code"
  operator: ai
  instruction: "Status should indicate a successful response"

- type: text
  content: RESPONSE_TEXT       # input key → resolvedInputs[RESPONSE_TEXT]
  operator: ai
  instruction: "Body should not contain any error messages"

# Without content — evaluates full response body:
- type: text
  operator: ai
  instruction: "Body should not contain any error messages"
```

`{{ }}` references in `instruction` are resolved before the AI call.

> ℹ An `ai` assertion is a **non-deterministic** model judgement, and the asserted value is sent to a third-party provider. Prefer a deterministic operator where certainty matters; see `SYZ-NOTICE.md` (AI risk + data egress).

### All assertion operators

| Operator | Applicable types | Notes |
|---|---|---|
| `equals` | json, text, http | Strict equality |
| `not_equals` | json, text, http | |
| `exists` | json, text, http | Value is non-null and non-undefined |
| `not_exists` | json, text, http | |
| `contains` | text: substring; json: array membership | |
| `not_contains` | text, json | |
| `matches` | text, json | Regex |
| `in` | json, text | Value is one of an array |
| `not_in` | json, text | |
| `greater_than` | json | Numeric |
| `less_than` | json | |
| `greater_than_or_equal` | json | |
| `less_than_or_equal` | json | |
| `matches_schema` | json | JSON schema validation |
| `all` | json | Every item in JSONPath array satisfies sub-checks |
| `any` | json | At least one item satisfies sub-checks |
| `count_equals` | json | Count of JSONPath array results equals value |
| `expression` | json | Arbitrary JS boolean expression; `response` and `inputs` are in scope — must return boolean |

For *which* operator to reach for, see *Choosing the right operator* in `SYZ-GUIDELINES.md`.

### `value_from_input`

Makes a validate procedure reusable across scenarios with different expected values:

```yaml
# In the validate procedure checks:
- type: http
  path: "$.fields.status_code"
  operator: equals
  value_from_input: expected_status   ← looks up "expected_status" in the step's resolved inputs

# In Scenario A:
- type: validate
  procedure: payments.validate_order_response
  inputs:
    response:        "{{ ledger.payments.send_order.http.response }}"
    expected_status: 201

# In Scenario B (same procedure, different expectation):
- type: validate
  procedure: payments.validate_order_response
  inputs:
    response:        "{{ ledger.payments.send_order.http.response }}"
    expected_status: 400
```

### Hand-authoring a plugin

Five steps to create a plugin from scratch:

1. **Create the plugin directory structure:**

   ```bash
   mkdir -p .syz/plugins/<name>/{procedures,templates,models}
   ```

2. **Create `plugin.yaml`** with name and version (see schema below).

3. **Write your first send procedure** in `procedures/<name>.yaml` — see the send procedure schema below.

4. **Write your first template** in `templates/<name>.njk` — a Nunjucks file that renders the request body using resolved input values.

5. **Reference the procedure from a scenario → `syz lint --env <name>` → `syz run --suite ... --env <name>`**

Start with a single send procedure and one template; add validate, craft, and workflow procedures as the integration grows. Capture the integration's behaviour and rules in the plugin's `PLUGIN-GUIDE.yaml` (scaffolded by `syz generate plugin`; create it by hand otherwise) so scenario authors know how it is meant to be used.

### Worked example — `payments` plugin from zero to passing run

A complete end-to-end walkthrough. Every file shown is the minimum needed.

**1. Scaffold the directories:**

```bash

```

**2. `.syz/plugins/payments/plugin.yaml`:**

```yaml

version: 1.0.0
```

**3. `.syz/plugins/payments/procedures/send_order.yaml` (send procedure):**

```yaml
name: payments.send_order
type: send
execution_library: http
description: "POST a new order to the payments service"
outputs:
  orderId:
    path: "$.fields.body.orderId"
```

(No `.njk` template — structured fields replace it. `syz generate` emits **one** `http:` block holding both connection identity and the operation — no separate `connection:` block and no `lifecycle` field (lifecycle is derived structurally from the executor). The identity file for a plugin — name and version only.

### Send procedure YAML (`procedures/<name>.yaml`)

All metadata lives directly in the procedure YAML — no separate manifest file.

```yaml
name: payments.send_order
type: send
execution_library: http
description: "POST a new order to the payments service"
outputs:
  orderId:
    path: "$.fields.body.orderId"
    description: "Created order ID"
  httpStatus:
    path: "$.fields.status_code"
    description: "HTTP status"
http:                                # ONE executor block — identity AND operation
  request:
    fields:
      base_url: "{{ env.payments.send_order.base_url }}"   # location identity, via env
      method: POST
      path: /orders
      body: { type: raw, content: "{{ inputs.order }}" }
    headers:
      Authorization: "Bearer {{ env.payments.send_order.auth_token }}"  # secret → env → os-env-var
sensitive_fields:                    # emitted AFTER the block (read the fields first)
  - request.headers.Authorization    # defence in depth (Authorization is auto-masked by name)
```

This single-block shape is exactly what `syz generate` emits — connection identity (`base_url`, auth header) folded into the same `http:` block as the operation (`method`, `path`, `body`). There is **no `connection:` block** and **no `lifecycle` field** on a generated procedure; lifecycle is derived structurally from the executor (stateless → ephemeral, stateful → keep_alive).

A separate procedure-level `connection:` block remains a **valid hand-authoring option** when you want to keep shared identity visually distinct from the operation — it wraps the executor block (`{ execution_library, http: { request, settings } }`) and deep-merges with the procedure's own `http:` block under the same precedence. Reach for it only when that separation earns its keep; otherwise prefer the single block.

**Key procedure rules:**
- Procedure names are fully qualified: `<plugin>.<procedure-name>`
- The procedure's `http:` block is the **base identity AND the operation**; a step's `connection: <name>` composes any env/scenario `connections.<name>` handle over it under the single precedence `step > scenario > procedure > env` (see *Named connections* above). An optional procedure `connection:` block, if present, contributes the same base-identity layer. `defaults` still seed `{{ inputs.* }}` values.
- `sensitive_fields` use dot-notation paths rooted at `request.`/`settings.`/`response.`; masked values are replaced with `[MASKED]`. `Authorization`/`Cookie`/`Proxy-Authorization` headers and tls/proxy secrets are masked automatically.
- `outputs` are JSONPath shortcuts into the response object — accessible as `{{ ledger.<procedure>.outputs.<field> }}`
- Identity on the procedure (whether in the `http:` block or an optional `connection:` block) is **secret-free by contract** (only `{{ os-env-var:NAME }}` / `{{ env.x.y }}` references and non-secret literals — a literal secret is `LITERAL_CREDENTIAL_IN_CONNECTION`; a literal *location* field raises `LITERAL_IDENTITY_IN_PROCEDURE_BLOCK`).

### Craft procedure YAML (`procedures/<name>.yaml`)

Produces a local artifact (XML, JSON, CSV, etc.) without making a network call. The content is stored in the ledger and optionally written to disk. The `crafter` field selects the content-generation strategy — defaults to `nunjucks` when absent.

#### Crafter: nunjucks (default)

Renders a Nunjucks template using resolved inputs as the template context.

```yaml
name: mq.craft_order_message
type: craft
crafter: nunjucks          # optional — this is the default when crafter is absent
template: templates/order_message.xml.njk
output_to_file: "order_message.xml"   # optional — absent = in-memory only; supports {{ }} expressions
```

#### Crafter: ai

Calls the OpenAI-compatible AI API (configured in `.syz/ai-api.yaml`) to generate the content. `instruction` is required. `template` is optional — when present, the raw file content is appended to the AI prompt as a reference for structural consistency.

```yaml
name: mq.craft_invoice_xml
type: craft
crafter: ai
instruction: "Generate a valid XML invoice for orderId {{ orderId }} with amount {{ amount }} {{ currency }}"
template: templates/invoice_schema.xsd   # optional — any file type, sent raw as a reference
output_to_file: "invoice.xml"            # optional
```

- `instruction` supports `{{ inputName }}` expressions resolved from the step's resolved inputs
- The reference template is read raw (not Nunjucks-rendered) and appended to the user message
- The AI is called with `temperature: 0` for deterministic output
- `crafter: ai` without `instruction` is a lint error

**Craft procedure with outputs declared inline:**
```yaml
name: mq.craft_order_message
type: craft
crafter: nunjucks
description: "Renders the MQ order message XML from inputs"
outputs:
  filePath:
    path: "$.metadata.output_file_path"
    description: "Path to written file"
sensitive_fields: []
defaults:
  orderId:  "{{ plugin.mq.data.craft_order_message.orderId }}"
  amount:   "{{ plugin.mq.data.craft_order_message.amount }}"
  currency: "{{ plugin.mq.data.craft_order_message.currency }}"
output_to_file: "order_message.xml"
template: templates/order_message.xml.njk
```

**Key craft rules:**
- `execution_library` is not set — craft procedures have no executor
- `crafter` field is optional — omitting it defaults to `nunjucks`
- `body` is always populated in the ledger with the full rendered content (the parsed JSON value when the crafter output looks like JSON, otherwise the raw text)
- When `output_to_file` is declared, the file is written to `.syz/results/<run-id>/<scenario-id>/crafted/<procedure-name>/<filename>`
- `metadata.output_file_path` is set only when a file is written
- `output_to_file` supports `{{ }}` expressions resolved at runtime (e.g. `"{{ outline.orderId }}_order.xml"`)

### Workflow procedure YAML

```yaml
name: payments.workflow_checkout
type: workflow
steps:
  - procedure: payments.send_order
    inputs:
      userId:   "{{ payments.data.users.primary_id }}"
      amount:   100
      currency: "GBP"

  - procedure: payments.validate_order_response
    inputs:
      response:        "{{ ledger.payments.send_order.http.response }}"
      expected_status: 201
```

**Generated `<slug>_send_success` workflows.** `syz generate` emits one thin workflow per send procedure that runs the send, then feeds its response into a single shared `validate_send_no_error` procedure (one per plugin) asserting `$.error` `not_exists`. This is the first-class "did the send work?" check — a send never judges itself (transport/protocol negatives are captured as `body.error` **data**, not thrown), so this workflow is what turns a clean send into a pass. **This is the preferred way to express a successful send** — reach for the `<slug>_send_success` workflow step rather than hand-chaining a `send` + `validate_send_no_error` pair; only hand-chain the explicit pair (or a bespoke validate) when a negative-path test asserts **on the send's `body.error` itself**. A stateful send step also carries a default `connection: send_<slug>` handle name.

```yaml
name: payments.create_order_send_success
type: workflow
steps:
  - procedure: payments.send_create_order
    inputs: {}
  - procedure: payments.validate_send_no_error
    inputs:
      response: "{{ ledger.payments.send_create_order.http.response }}"
```

### HTTP requests — the structured `http` block

An `http` send procedure authors its request as a structured `http: { request: { fields, headers }, settings }` block — no `.njk` template. Every part is layerable through the connection precedence; `{{ }}` references (incl. `{{ inputs.* }}`) are resolved before the request is built.

```yaml
http:
  request:
    fields:
      method: POST                          # GET|POST|PUT|DELETE|PATCH|HEAD|OPTIONS
      base_url: "https://api.example.com"   # location — OR a full `url:` (mutually exclusive)
      path: "/v1/orders"                    # joined to base_url with a single slash
      query: { limit: 50, id: [1, 2] }      # arrays → repeat-key by default (?id=1&id=2)
      body: { type: raw, content: "{{ inputs.order }}" }
    headers:                                # OPEN namespace — any key allowed
      Authorization: "Bearer {{ env.api.token }}"   # auto-masked
      Accept: "application/json"
  settings:                                 # transport tuning (closed set)
    timeout_ms: 30000                       # default 30000
    follow_redirects: true                  # default true
    max_redirects: 5                        # default 5
    tls:   { verify: true, ca_cert: "./ca.pem", client_cert: "./c.pem", client_key: "./k.pem", client_key_passphrase: "{{ os-env-var:KEY_PASS }}" }
    proxy: { url: "http://corp-proxy:8080", username: "{{ os-env-var:PROXY_USER }}", password: "{{ os-env-var:PROXY_PASS }}" }
    query_array_format: repeat              # repeat | bracket | comma
    max_capture_bytes: 5242880              # response-body capture cap; default ~5 MB (truncated bodies marked, never silently lost)
```

**URL — two modes (mutually exclusive).** `base_url` + `path` (single-slash normalised at the seam) **or** a full `url`. Setting both is `URL_MODE_CONFLICT`; neither is `URL_MISSING`. (No request-side `http_version` — it is observed on the response.)

**Body.** `body.type ∈ none | form-data | x-www-form-urlencoded | raw | binary`. A file is **always** an explicit `{ file: "<path>", filename?, content_type? }` — never a bare path. Paths are relative to the project root; absolute allowed.

| `body.type` | `content` is | files | default Content-Type |
|---|---|---|---|
| `none` | absent | — | — |
| `form-data` | key→(text | `{ file }`) map | many | `multipart/form-data` (framework-owned boundary) |
| `x-www-form-urlencoded` | flat key→**text** map | **none** | `application/x-www-form-urlencoded` |
| `raw` | object (→JSON) / string / single `{ file }` (content inlined) | 1 | object→`application/json`, else `text/plain` |
| `binary` | exactly one `{ file }` (bytes streamed) | 1 | file `content_type` or `application/octet-stream` |

An explicit `Content-Type` header wins **except** for `form-data` (the framework owns the multipart boundary). The header only labels the body — it never rewrites it: a `raw` **string** is sent **verbatim** on the wire regardless of `Content-Type`, and an object is serialised to JSON. For a JSON body, author an **object** (`content: { ... }`) or a string that is valid JSON. A `raw` string declared `application/json` that is **not** valid JSON still goes out verbatim (so a deliberately malformed negative test reaches the server intact) and raises the non-blocking warning `BODY_RAW_NOT_JSON` to flag accidental typos. A **dynamic** body (loops/conditionals) is built by a `craft` step and referenced: `body: { type: raw, content: "{{ ledger.<plugin>.<craft>.response.body }}" }`.

**Settings — `tls` / `proxy`.** `tls`: `verify` (default `true`; `false` accepts self-signed), `ca_cert`, `client_cert`, `client_key`, `client_key_passphrase`. `proxy`: `{ url, username, password }`.

**Lint.** Errors block the run: `INVALID_HTTP_METHOD`, `MISSING_HTTP_METHOD`, `URL_MODE_CONFLICT`, `URL_MISSING`, and the body matrix (`BODY_TYPE_REQUIRED`, `INVALID_BODY_TYPE`, `BODY_NONE_WITH_CONTENT`, `BODY_CONTENT_REQUIRED`, `BODY_FORMDATA_SHAPE`, `BODY_URLENCODED_SHAPE`, `BODY_URLENCODED_FILE`, `BODY_RAW_MULTIPLE_FILES`, `BODY_BINARY_SHAPE`, `BODY_BINARY_MULTIPLE`). Warnings surface but don't block: `UNKNOWN_HTTP_REQUEST_FIELD`, `UNKNOWN_HTTP_SETTING`, `BODY_ON_BODYLESS_METHOD`, `CONTENT_TYPE_CONFLICT`, `LITERAL_IDENTITY_IN_PROCEDURE_BLOCK`. **Header keys are never allowlisted.**

**Examples:**

```yaml
# x-www-form-urlencoded login
http:
  request:
    fields:
      method: POST
      base_url: "{{ env.api.base_url }}"
      path: /login
      body: { type: x-www-form-urlencoded, content: { username: "{{ inputs.user }}", password: "{{ os-env-var:PW }}" } }
```

```yaml
# multipart upload (text field + file)
http:
  request:
    fields:
      method: POST
      url: "https://api.example.com/upload"
      body:
        type: form-data
        content:
          description: "{{ inputs.description }}"
          file: { file: "{{ inputs.filePath }}", content_type: "text/csv" }
```

```yaml
# binary upload + mTLS, redirects off
http:
  request:
    fields: { method: PUT, url: "https://api.example.com/blob", body: { type: binary, content: { file: "./report.pdf" } } }
  settings:
    follow_redirects: false
    tls: { client_cert: "./c.pem", client_key: "./k.pem", client_key_passphrase: "{{ os-env-var:KEY_PASS }}" }
```

## Knowledge layer — `DOMAIN.yaml` & `PLUGIN-GUIDE.yaml`

The knowledge layer captures **what the application does** as schema'd, lint-validated YAML. It is **user-owned** (scaffolded once, never overwritten — `PLUGIN-GUIDE.yaml` also ships with the plugin via `syz install`) and written in your own **domain language**: no syz / procedure / scenario / executor vocabulary, no plugin name or version (folder = name, `plugin.yaml` = version). Requirements are authored **before** plugins/procedures exist; the requirement→procedure binding happens later, at scenario-authoring time, via `covers:`.

- `PLUGIN-GUIDE.yaml` (L2, per plugin) — one integration's behaviour.
- `DOMAIN.yaml` (L3, workspace) — cross-integration journeys, opening with the `areas:` registry.

### Requirement schema

Every requirement has a **mandatory core** plus optional fields drawn from a **closed catalog** (`syz lint` rejects keys outside it — put anything else under `more_details:`).

| Field | Required | Meaning |
|---|---|---|
| `id` | ✓ | `REQ-<SCOPE>-<PG\|DOM>-<NNN>` (see below) |
| `behaviour` | ✓ | `given` / `when` / `then` — **each a string OR a list of strings** (a list = implicit AND). No `and`/`but`/`precondition` keywords |
| `notes` | ✓ | Human-facing prose. Humans read these files via `notes:` — write enough of it |
| `summary` | | One-line description |
| `inputs` | | Fields + real constraints: `type`/`min`/`max`/`values`/`required`/`format`/`example` |
| `outputs` | | What the operation returns |
| `preconditions` | | What must hold before |
| `rules` | | Plain-language domain rules |
| `effects` / `postconditions` | | What changes after |
| `lifecycle` | | States + legal/illegal transitions |
| `errors` | | The application's error semantics (`code` + `meaning`) |
| `data` / `examples` | | Concrete sample values |
| `references` | | Links to source requirement docs / tickets |
| `flow` | | **DOM only** — the cross-service journey in domain terms (not procedure references) |
| `more_details` | | Free-form map — the **single** escape hatch for anything outside the catalog |

There is deliberately **no `invariants`** field (too abstract — a hallucination magnet; captured knowledge must be concrete) and **no `operation`/procedure field** (a requirement predates any procedure).

### Requirement IDs — `REQ-<SCOPE>-<PG|DOM>-<NNN>`

The `PG`/`DOM` marker bakes the L2-component vs L3-E2E distinction into the pointer itself.

- **PG** scope = the **plugin folder name** (uppercased, hyphens → underscores): `REQ-PAYMENTS-PG-001` must live in `payments`' `PLUGIN-GUIDE.yaml`.
- **DOM** scope = a key from `DOMAIN.yaml`'s `areas:` registry: `REQ-CHECKOUT-DOM-001` requires `CHECKOUT` to be a declared `areas[].key`.
- `NNN` = any number of digits, next-free; **unique across the whole workspace**.

#### In-progress requirements — the `_` marker

Prefix an id with a leading underscore (`_REQ-CHECKOUT-DOM-001`) to mark a requirement **in progress / draft** — captured, but not yet ready to be tested. An in-progress requirement:

- is **excluded from the coverage floor** — `syz lint` raises no `UNCOVERED_REQUIREMENT` for it;
- is **excluded from `syz rtm`** — it never appears as an uncovered row (the report notes how many were excluded);
- is **still fully validated** — id grammar, layer/scope, and workspace-uniqueness all still apply, so a draft cannot silently rot;
- **warns if a test covers it** — a `covers:` that resolves to an in-progress requirement is a `COVERS_INPROGRESS_REQUIREMENT` warning (you should not discharge coverage against work still in flight).

The `_` is only a **status marker, not part of the identity**: `_REQ-X` and `REQ-X` are the same requirement. Promote a draft by **deleting the underscore** — every test that already wrote `covers: REQ-X` stays valid, and defining both `_REQ-X` and `REQ-X` is a `DUPLICATE_REQUIREMENT_ID`.

### `DOMAIN.yaml` shape

```yaml
areas:                                  # the registry — DOM scopes must be a key here
  - { key: CHECKOUT, title: "Checkout & payment", description: "cart → pay → fulfil → notify" }
entities:                               # optional — the ids that link services
  order: { id: order.id, links: [payment.order_id, shipment.order_id] }
requirements:
  - id: REQ-CHECKOUT-DOM-001
    behaviour:
      given: a placed order with a valid payment method
      when:  the order is paid
      then:  [payment settles, fulfilment begins, the customer is notified]   # list = AND
    flow:
      - the customer pays for the order
      - fulfilment begins once payment has settled
    rules:
      - fulfilment must not begin until payment has settled
    notes: >
      Settlement may be delayed (asynchronous).
```

### `PLUGIN-GUIDE.yaml` shape

```yaml
summary: >
  Charges, captures, and refunds customer payments for orders.
requirements:
  - id: REQ-PAYMENTS-PG-001
    behaviour:
      given: a valid card and a supported currency
      when:  a payment is made for a positive amount
      then:  the payment is captured and a payment reference is returned
    inputs:
      - { field: amount,   type: integer, min: 1, max: 1000000, required: true }
      - { field: currency, type: string,  values: [USD, EUR, GBP], required: true }
    rules:
      - amount must be between 1 and 1,000,000
      - a declined card is refused and nothing is charged
    errors:
      - { code: DECLINED, meaning: the issuer refused the charge }
    notes: >
      The maximum is a business limit. A declined card is a normal, expected outcome.
```

`syz lint` validates these files (schema, ID format/uniqueness, layer/scope, `areas` membership). Link tests to requirements with `covers:` and report coverage with `syz rtm` (both below).

### `guidelines:` — binding authoring rules (the HOW)

Alongside `requirements:`, both `PLUGIN-GUIDE.yaml` and `DOMAIN.yaml` accept an optional top-level **`guidelines:`** list. A guideline is a rule the authoring agent must **obey when constructing** a procedure/scenario or choosing/configuring an executor (the HOW) — as opposed to a requirement, which is a behaviour the tests verify (the WHAT). Guidelines are **never executed or asserted** and carry **no `covers:`** / never appear in `syz rtm`. Unlike requirements, a guideline **may** name mechanics — executors, headers, TLS, settings — since steering them is its purpose. (For *when* to record one vs a requirement, see `SYZ-GUIDELINES.md`.)

```yaml
guidelines:
  - id: GL-PAYMENTS-001                 # required, workspace-unique
    affects: "all requests to the payments service"
    rule:    "requests must include the header X-Api-Version: 2"
    cause:   "payments service platform upgrade (2026-Q2)"
    impact:  "absent → 400 UNSUPPORTED_VERSION"
    reference: "JIRA PAY-1847"
```

| Field | Required | Notes |
|---|---|---|
| `id` | ✓ | `GL-<SCOPE>-<NNN>` (see below) |
| `rule` | ✓ | the binding imperative the author must apply |
| `affects` | | the scope the rule applies to, in prose |
| `cause` | | why the rule exists (the technology change that forced it) |
| `impact` | | what happens if it is not followed |
| `reference` | | link to the ticket / upgrade note |

**Guideline IDs — `GL-<SCOPE>-<NNN>`.** Uppercase `SCOPE` token, then digits. **No `PG`/`DOM` marker** (guidelines have no `covers:`, so the layer marker would earn nothing). `SCOPE` is validated **by file location**: a guideline in a `PLUGIN-GUIDE.yaml` uses the **plugin folder** scope (`GL-PAYMENTS-001` in `payments`); one in `DOMAIN.yaml` uses a declared **`areas[].key`** (`GL-CHECKOUT-001`). IDs are workspace-globally unique. When you implement a guideline in a procedure, drop a `# see GL-<id>` comment at the point of implementation.

## Environments & secrets

```yaml
name: local
production: false
allow_destructive_operations: true

payments:
  # Generated by syz generate — one block per send procedure, keyed <plugin>.send_<slug>.
  # These are the identity fields the procedure's connection block references via {{ env.payments.send_<slug>.<field> }}.
  send_create_order:
    url:        "http://localhost:3000/orders"   ← http connectionField — the FULL request URL
    auth_token: "{{ os-env-var:PAYMENTS_AUTH_TOKEN }}"   ← secret via os-env-var — plugin-scoped, so every entry below shares it
  send_get_order:
    url:        "http://localhost:3000/orders"   ← host only; the {path} param lives in the procedure http block as {{ ctx.var.orderId }}, wired by hand via a set:
    auth_token: "{{ os-env-var:PAYMENTS_AUTH_TOKEN }}"   ← same variable: one plugin = one upstream system = one credential

  # Hand-authored keys coexist alongside the generated blocks above.
  token:      "{{ env.shared.api_key }}"   ← cross-reference another system in the same file
  timeout_ms: 5000                         ← optional — HTTP request timeout in ms. Default: 30000

shared:
  api_key: "local-dev-token"
```

```yaml
# {{ os-env-var:NAME }} — injects process.env[NAME], masked everywhere, safe to commit
name: production
production: true

payments:
  base_url:  "{{ os-env-var:PAYMENTS_BASE_URL }}"
  api_key:   "Bearer {{ os-env-var:PAYMENTS_API_KEY }}"   ← inline interpolation works
```

**`{{ os-env-var:NAME }}` resolution in environment files:** any string field may inject an OS environment variable via `{{ os-env-var:NAME }}`. It uses the unified `{{ }}` grammar, so inline interpolation works (`"Bearer {{ os-env-var:TOKEN }}"`) — it does not have to be the whole field value. The variable is read from `process.env[NAME]` at load time. If the variable is **unset or empty**, the literal `{{ os-env-var:NAME }}` is preserved (never silently empty) so `syz lint` and runtime resolution surface it as `<NAME> not set in current environment`. **Every resolved `os-env-var` value is treated as a secret and masked (`[MASKED]`) in all recorded and displayed output** (terminal, `debug.log`, `ledger.json`, `execution.json`, `index.html`, `junit.xml`) — only the live outbound request carries the real value. Masking is **location-first**: the field a secret is injected into is blanked by path, at any length. The global value-net (substring scrub) is a defence-in-depth layer that only holds values `>= 5` chars (the `MIN_SECRET_LENGTH` floor) — a sub-floor value (e.g. a `"x"` placeholder) is **never** globally scrubbed, because substring-matching a 1-char value would corrupt incidental text (`flex`, `example-status`) and the rendered report. A genuinely short secret is still masked at its known location; the only uncovered corner is a short value a server **echoes** into a field you neither injected nor declared — declare that field in `sensitive_fields`. For non-secret OS-derived config you want visible in artifacts, use a plain literal or `{{ env.x.y }}` cross-reference instead.

> The legacy `${VAR}` and `env:VAR` forms are removed. Use `{{ os-env-var:NAME }}` everywhere.

Plugin keys sit directly at the top level alongside `name` and `production`. The step procedure resolves `env[pluginName]` to find the system config for a procedure's execution and template context.

**Environment file location:** `.syz/environments/<env-name>.yaml`

Selected at run time with `syz run --env <env-name>` (and `syz lint --env <env-name>`) — the `<env-name>` maps to the file's `name` field. A scenario never names an environment itself, so the same scenario runs unchanged against any environment you point `--env` at.

**`production`** and **`allow_destructive_operations`**: both flags are stored in execution metadata and shown in reports. MVP does not gate any runtime behaviour on them — teams that want enforcement wire it in their own CI.

### `dependency.json`

Declares plugin dependencies installed from git. Lives at `.syz/dependency.json`. Managed by `syz install`.

```json
{
  "plugins": [
    {
      "name": "payments",
      "git": "https://github.com/acme/payments-plugin.git",
      "version": "v1.2.0"
    },
```

`name` is the local alias. It must match the folder name under `.syz/plugins/` in the source repository. `version` is a git tag. Installed plugins land in `.syz/plugins.installed/<name>/` — never committed, auto-added to `.gitignore`.

### Executor drivers — provisioned on demand

The `syz` package itself stays lean: it bundles only the core CLI, **not** the client libraries that executors talk to brokers, databases, queues, or browsers with (`kafkajs`, `amqplib`, `ssh2`, `pg`/`mysql2`/`tedious`/`knex`/`oracledb`/`better-sqlite3`, `mongodb`, `ioredis`, the `@aws-sdk/*` packages, `playwright`). Those are **provisioned on demand**, driven by the executors your plugins actually declare — a project that only uses `http` pulls nothing extra.

- **What triggers it.** `syz install` (after fetching a plugin), `syz generate` (after authoring), and `syz run` (a pre-flight before any step) each scan the `execution_library` values declared across `.syz/plugins/*` and `.syz/plugins.installed/*`, then install any driver that is missing or out of the version range this `syz` release supports — into the **same npm scope as `syz`** (global when `syz` is global, local when local), so it resolves with zero extra config. You never list drivers anywhere; the plugin's procedures are the single source of truth.
- **Pure-JS drivers auto-install silently** (the default). **Native** modules (`oracledb`, `better-sqlite3`) and **browser binaries** (Playwright's `chromium`/`firefox`/`webkit`) ask for consent first, because they are heavier and build/download more — decline and `syz` prints the exact command to run yourself.
- **Opt out** with `--no-install` (on `run`, `install`, `generate`) or the `SYZ_NO_AUTO_INSTALL` environment variable (for CI). With auto-install off, a missing or out-of-range driver **fails fast** printing the exact `npm install …` command rather than installing anything.
- **CI / non-TTY.** Pure-JS drivers still auto-install (versions are pinned and deterministic); native/binary drivers never block — they fail fast with the command. Pass `--yes` to accept native/binary consent and push through non-interactively.
- **Driver versions are owned by your `syz` version**, never by plugins — so a shared plugin works across teams regardless of their local driver state, and upgrading `syz` reprovisions any driver whose supported range moved.

### AI API Config (`.syz/ai-api.yaml`)

Required when any `{{ ai: }}` resolver expression or `operator: ai` assertion is used. Written by `syz init` if absent — with empty values; configure before invoking any AI feature. Safe to commit when using the `{{ os-env-var:NAME }}` syntax.

The starter file `syz init` writes:

```yaml
# Configure to enable ai based feature e.g., {{ ai: ... }} resolvers and `type: ai` assertions.
# Any OpenAI-compatible provider works (Anthropic, OpenAI, Azure, Ollama, LM Studio, etc.).
#
# Example — os-env-var form (resolved from process.env, masked everywhere, safe to commit):
#   ai:
#     base_url: https://api.anthropic.com/v1
#     model: claude-haiku-4-5-20251001
#     api_key: "{{ os-env-var:ANTHROPIC_API_KEY }}"
#
# Example — literal form (for Vault / Doppler / 1Password CLI, do not commit):
#   ai:
#     base_url: https://api.anthropic.com/v1
#     model: claude-haiku-4-5-20251001
#     api_key: sk-ant-...
ai:
  base_url: ''
  model: ''
  api_key: ''
  max_tokens: 256
```

**`{{ os-env-var:NAME }}` resolution:** any string field (`base_url`, `model`, `api_key`) may inject `process.env[NAME]` at load time, including inline. A resolved `api_key` is registered as a secret and masked everywhere it could otherwise surface (errors, traces, debug log). An unset variable leaves the literal `{{ os-env-var:NAME }}` in place, which counts as empty for the required fields → `AI_CONFIG_INCOMPLETE`.

- File missing → `AI_CONFIG_NOT_FOUND`.

## Commands reference

### `syz run`

Run scenarios against an environment.

```bash
syz run --suite <path> --env <name>
syz run --suite .syz/scenarios/e2e/checkout.yaml --env local
syz run --suite .syz/scenarios/e2e/ --env staging
syz run --suite .syz/scenarios/ --env local --run-name my-run
syz run --suite .syz/scenarios/ --env local --live-stats
syz run --suite .syz/scenarios/ --env ci --reporter junit
syz run --suite .syz/scenarios/ --env ci --reporter junit --output ./ci/results.xml
syz run --suite .syz/scenarios/ --env local --continue-scenario-on-failure
```

| Flag | Description |
|---|---|
| `--suite <path>` | Path to a scenario file or directory (required) |
| `--env <name>` | Environment name — maps to `.syz/environments/<name>.yaml` (required) |
| `--run-name <id>` | Custom execution ID — used as results folder name |
| `--live-stats` | Open browser progress panel during execution |
| `--reporter junit` | Write a JUnit XML report at run end (consumed by GitHub Actions, GitLab CI, Jenkins, CircleCI, Azure DevOps) |
| `--output <path>` | Output path for the JUnit XML file — absolute or relative to cwd. Only valid with `--reporter junit`. Defaults to `.syz/results/<execution-id>/junit.xml` |
| `--continue-scenario-on-failure` | Keep running a scenario past a failed `validate` check so one run surfaces **every** failed validation, not just the first. `error`/`exception`/`aborted` still halt the scenario. Run-wide and CLI-only — there is no scenario/procedure/env field. Never changes the verdict: a scenario with ≥1 `failure` still reports `failure` and exit `1`. Recorded in `execution.json` (`continue_scenario_on_failure`), shown as a header badge in `index.html`, and annotated in `debug.log` under each continued-past failure |
| `--no-install` | Skip on-demand driver provisioning for this run (drivers must already be present; missing ones fail fast at pre-flight) |
| `--yes` | Accept native/browser-binary driver provisioning consent non-interactively |

**Exit codes:**

| Code | Meaning |
|---|---|
| `0` | All scenarios passed every assertion |
| `1` | At least one scenario failed, OR a top-level error (invalid config, missing plugin, schema error, etc.) |
| `130` | Interrupted by `SIGINT` (Ctrl-C) — results written so far remain on disk |

CI pipelines should fail the build on any non-zero exit.

### `syz install`

Install plugin dependencies from git.

```bash
syz install                                                  # install all from dependency.json
syz install https://github.com/acme/payments.git@v1.2.0 --plugin payments
syz install https://github.com/acme/payments.git@v1.2.0 --plugin payments --force
```

| Flag | Description |
|---|---|
| `--plugin <name>` | Plugin name (required for single-plugin form) |
| `--force` | Re-install even if present; overwrite dependency.json entry |
| `--no-install` | Skip on-demand driver provisioning after fetching the plugin |

An installed plugin ships with its `PLUGIN-GUIDE.yaml` (the publisher's integration knowledge) and its `CLAUDE.md` pointer (`@PLUGIN-GUIDE.yaml`) — both arrive via the sparse-checkout, and a consumer never edits the installed copy.

### `syz generate`

Generate a full plugin from an OpenAPI spec or Postman collection — or a spec-less guide-first plugin shell (`--guide-only`).

```bash
syz generate plugin --name payments --from openapi:./spec.yaml
syz generate plugin --name orders --from postman:./collection.json
syz generate plugin --name payments --from openapi:./spec.yaml --force
syz generate plugin --name payments --from openapi:./spec.yaml --overwrite
syz generate plugin --name payments --from openapi:./spec.yaml --dry-run
syz generate plugin --name payments --from openapi:./spec.yaml --yes
syz generate plugin --name payments --guide-only
```

| Flag | Description |
|---|---|
| `--name <name>` | Plugin name — folder name and procedure FQN prefix (required) |
| `--from <source>` | Source: `openapi:<path>`, `postman:<path>`, or `prompt` (the interactive walkthrough — the default when `--from` is omitted) |
| `--guide-only` | Scaffold a **spec-less, knowledge-only plugin shell** — record behaviour before any endpoint or spec exists. Incompatible with `--from`/`--force`/`--overwrite`; see *Guide-first plugins* below |
| `--force` | Regenerate the plugin from scratch — clears generated procedures/models/templates and the generated scenarios, but **preserves every non-`SYZ-` user file** (your `PLUGIN-GUIDE.yaml`, `README.md`) |
| `--overwrite` | Replace selected operations only; preserve others |
| `--dry-run` | Print files that would be written without writing them (works with `--guide-only` too) |
| `--yes` | Skip interactive prompts — generate all operations without confirmation. Also applied automatically when `stdin` is not a TTY (CI / piped input). |

**What it generates (per operation):**
- A **send procedure** `procedures/send_<slug>.yaml` carrying **one** `http:` executor block that holds **both** the connection identity and the operation — **no** separate `connection:` block and **no** `lifecycle` field (the runtime derives lifecycle structurally from the executor: stateless `http` → ephemeral, stateful → keep_alive), no `.njk` template. The block's `request.fields.base_url` is a `{{ env.<plugin>.send_<slug>.base_url }}` reference; `method`/`path`/`body` are the operation; and, for executors with a secret auth field, `request.headers.Authorization` is `Bearer {{ env.<plugin>.send_<slug>.auth_token }}` (the env file maps `auth_token` to `{{ os-env-var:<PLUGIN>_<FIELD> }}`, SCREAMING_SNAKE — a two-hop reference; the OS variable is **plugin-scoped**, shared by every send procedure of the plugin, while the `{{ env.* }}` reference stays per-procedure). Any OpenAPI/Postman **path parameter** is emitted into `path` as `{{ ctx.var.<param> }}` (no scaffolded setter — wire its source with a `set:` block, see *Context variables*; an unwired var fails `syz lint` with `UNKNOWN_CONTEXT_VAR`). `http.request.headers.Authorization` is added to `sensitive_fields` (which sits **after** the executor block) — defence in depth alongside the auto-masking of that header by name.
- A thin **`<slug>_send_success` workflow** `procedures/<slug>_send_success.yaml` — runs the send, then feeds `{{ ledger.<plugin>.send_<slug>.http.response }}` into the shared validate. This is the first-class "did the send work?" check and the **preferred** way to express a successful send — use this workflow step instead of hand-chaining a `send` + `validate_send_no_error` pair (hand-chain only to assert on `body.error` for a negative path). A stateful send step also carries a default `connection:` handle name (`send_<slug>`).

**What it generates (once per plugin):**
- One shared **`validate_send_no_error`** validate procedure (input model `models/validate_send_no_error_input.yaml`, single check `$.error` `not_exists`) — every `*_send_success` workflow reuses it.
- A guided **`PLUGIN-GUIDE.yaml`** stub (only if absent — never overwritten, even by `--force`) and a plugin `CLAUDE.md` pointer (`@PLUGIN-GUIDE.yaml`). Fill in the guide with the integration's behaviour and rules.

**Guide-first plugins (`--guide-only`):** `syz generate plugin --name <name> --guide-only` scaffolds a knowledge-only plugin shell — a complete deliverable for a business analyst, product owner, or domain SME who records what an integration *should do* before any endpoint or spec exists (and who may never author a test). It writes exactly three files under `.syz/plugins/<name>/` and nothing else:

- `PLUGIN-GUIDE.yaml` — the guided stub; fill in `requirements:` (and optionally `guidelines:`) in domain language
- `plugin.yaml` — identity only (`plugin: <name>`, `version: 1.0.0`) — this makes the shell discoverable, so `syz lint` validates the recorded requirements and `syz rtm` reports their coverage (0% until scenarios link them via `covers:`)
- `CLAUDE.md` — the `@PLUGIN-GUIDE.yaml` pointer

No procedures, models, templates, `data.yaml`, scenarios, env seeding, or driver provisioning are produced. Later, when the spec exists, `syz generate plugin --name <name> --from openapi:<spec>` fills in the executable artifacts on the **same** folder and preserves the hand-edited `PLUGIN-GUIDE.yaml`. Guardrails: `--guide-only` combined with `--from`, `--force`, or `--overwrite` is rejected (`INCOMPATIBLE_GUIDE_ONLY_FLAGS` — guide-only is spec-less and never overwrites); if `.syz/plugins/<name>/` already exists — in any state — it stops (`PLUGIN_FOLDER_EXISTS`) rather than risk touching existing knowledge. `--dry-run --guide-only` prints the three files without writing.

**Env wiring (`.syz/environments/local.yaml`):** `syz generate` seeds one entry per send procedure under `<plugin>.send_<slug>` — `base_url` (the host) and, for executors with secret fields, `auth_token: "{{ os-env-var:<PLUGIN>_<FIELD> }}"` (SCREAMING_SNAKE — e.g. plugin `payments` + field `auth_token` → `PAYMENTS_AUTH_TOKEN`). The operation `path` (with any `{path}` params rendered as `{{ ctx.var.<param> }}` reads — wire the source with a `set:` block, see *Context variables*) lives in the procedure's `http` block, not in env. Seeding is **idempotent and add-only** — existing keys are never overwritten, so re-running `generate` is safe. Export the named OS variables before `syz run`; an unset one surfaces as `<NAME> not set in current environment` at lint/run time.

**The seeded secret name is plugin-scoped, not per-operation.** Every send procedure of a plugin is seeded with the **same** `{{ os-env-var:<PLUGIN>_<FIELD> }}` name, because one plugin is one upstream system and therefore one credential set — so **one export runs every scenario for that plugin**, and rotating the credential is one change, not N. The repetition across entries is intentional and states something true ("these read the same secret"); the name stays deterministic and collision-free **across plugins**, which is the boundary that matters in a workspace holding several. **Escape hatch — a genuinely per-operation credential:** edit that one entry to a distinct variable (e.g. `send_refund.auth_token: "{{ os-env-var:PAYMENTS_REFUND_TOKEN }}"`) and export it. Add-only merge protects the edit permanently — re-running `generate` never overwrites it — while newly generated operations still arrive on the shared name. The env file stays fully explicit either way: every procedure states its own value, so the override point is local to the procedure that needs it.

### `syz lint`

Pre-flight check without executing anything. `lint` has **two modes** and requires **exactly one** — it never infers a default:

- **`--env <name>`** — the full pre-flight: scenarios, plugins, procedures **and** the environment.
- **`--knowledge`** — the knowledge layer only: `DOMAIN.yaml` + every `PLUGIN-GUIDE.yaml`. Reads **no** environment, **no** scenarios and **no** procedures, so it works the moment requirements are written — before any endpoint, spec, or environment file exists.

Passing neither is an error (`MISSING_LINT_MODE`), as is passing both (`INCOMPATIBLE_KNOWLEDGE_FLAGS`).

```bash
syz lint --env <name>
syz lint --env staging
syz lint --env staging --plugin payments
syz lint --env staging --plugin payments --suite .syz/scenarios/e2e/
syz lint --env staging --suite .syz/scenarios/e2e/checkout.yaml
syz lint --env staging --json

syz lint --knowledge                      # validate DOMAIN.yaml + every PLUGIN-GUIDE.yaml
syz lint --knowledge --plugin payments    # scope the guides to one plugin (DOMAIN.yaml is still read)
syz lint --knowledge --json
```

| Flag | Description |
|---|---|
| `--env <name>` | Environment name — maps to `.syz/environments/<name>.yaml`. Required **unless** `--knowledge` is given. |
| `--knowledge` | Validate only the knowledge layer. No environment, scenarios, or procedures are read. Mutually exclusive with `--env`. |
| `--plugin <name>` | Scope lint to scenarios referencing this plugin. Required when multiple local plugins exist. Legal in **both** modes: with `--knowledge` it scopes to that plugin's `PLUGIN-GUIDE.yaml` (`DOMAIN.yaml` is always read as well, so a requirement id colliding across the two files is still caught), and it never triggers `MULTIPLE_PLUGINS` there — that error disambiguates *scenario* scoping, and knowledge mode reads no scenarios. |
| `--suite <path>` | Path to a scenario YAML file or directory. Defaults to all `.syz/scenarios/**/*.yaml`. **Rejected with `--knowledge`** (`INCOMPATIBLE_KNOWLEDGE_FLAGS`) — there are no scenarios to select. |
| `--json` | Emit the structured issue list as JSON to stdout instead of the human report. Each issue is `{ severity, category, file, message, hint? }`; the exit code is unchanged (1 if any `error`, else 0). Lets an authoring agent close the write → lint → fix loop on machine-readable output. Legal in both modes. |

`--tag` and `--example` (see *Selecting a subset*) are likewise rejected with `--knowledge`.

**`--json` output shape:**

```json
{
  "issues": [
    { "severity": "error", "category": "scenario", "file": ".syz/scenarios/e2e/checkout.yaml", "message": "procedure payments.unknown not found in any loaded plugin" }
  ],
  "errorCount": 1,
  "warningCount": 0,
  "summary": {
    "mode": "env",
    "requirements": 42,
    "inProgress": 3,
    "guidelines": 18,
    "covered": 39
  }
}
```

`summary` is the knowledge-layer census, emitted in **both** modes. It is summary data, not a finding: it never affects `errorCount` / `warningCount` or the exit code. `mode` is `env` | `knowledge`.

**Knowledge-mode report.** The `Pre-flight:` header becomes `Knowledge check: <workspace>`, the Environment / Scenarios / Plugins blocks are omitted entirely, and the census is rendered as one line:

```
  Knowledge check: /path/to/workspace

  Knowledge (DOMAIN.yaml + PLUGIN-GUIDE.yaml)
      ⚠ requirement "_REQ-PAYMENTS-PG-001": notes: still contains the scaffold example text
        — replace it with the real narrative [PLACEHOLDER_KNOWLEDGE_CONTENT]

  42 requirements (3 in progress), 18 guidelines, 0 covered — no scenarios yet

  ⚠ knowledge layer valid (1 warning)
```

`severity` is `error` | `warning`; `category` is `scenario` | `plugin` | `environment` | `dependency` | `knowledge`.

**What it checks:**
- Every procedure in each scenario's flow exists in a loaded plugin
- `{{ ledger.x.y }}` expressions reference a procedure that appears earlier in the same flow
- `{{ outline.x }}` keys are present in every example row
- Referenced procedure `.yaml` files exist on disk and have valid structure
- Templates referenced by procedures exist in `templates/`
- Input models referenced by procedures exist in `models/`
- Environment file validates schema and each used plugin key is present
- All `{{ os-env-var:NAME }}` references in the env file resolve (the variable is set in the current shell) — any residual literal is reported as `<NAME> not set in current environment`
- All plugins referenced by scoped scenarios are present on disk
- `{{ ctx.var.x }}` reads (in scenario inputs **and** in referenced procedure bodies) have a matching `set:` somewhere in the resolved flow — else `UNKNOWN_CONTEXT_VAR` (error)
- No plugin / procedure / connection-handle / ctx-var / env-key identifier matches the reserved `/^syz/i` prefix — else `RESERVED_SYZ_IDENTIFIER` (error)
- **Knowledge layer** (`DOMAIN.yaml` / every `PLUGIN-GUIDE.yaml`): each requirement has the mandatory core (`id` + `behaviour` + `notes`) — else `MALFORMED_KNOWLEDGE_ENTRY`; ids match `REQ-<SCOPE>-<PG|DOM>-<NNN>` (`REQUIREMENT_ID_FORMAT`), are workspace-unique (`DUPLICATE_REQUIREMENT_ID`), sit in the right file (`REQUIREMENT_LAYER_MISMATCH`: `-PG-` only in a guide, `-DOM-` only in `DOMAIN.yaml`), and resolve their scope (`PG_SCOPE_MISMATCH`: PG scope = plugin folder; `UNKNOWN_DOMAIN_AREA`: DOM scope ∈ `areas[].key`). Each **guideline** has `id` + `rule` — else `MALFORMED_KNOWLEDGE_ENTRY`; ids match `GL-<SCOPE>-<NNN>` (`GUIDELINE_ID_FORMAT`), are workspace-unique (`DUPLICATE_GUIDELINE_ID`), and resolve their scope by file (`GUIDELINE_SCOPE_MISMATCH`: guide scope = plugin folder; `UNKNOWN_DOMAIN_AREA`: DOMAIN scope ∈ `areas[].key`); an unknown entry field is an `UNKNOWN_KNOWLEDGE_FIELD` warning
- `covers:` references resolve to an owned-PG or DOM requirement — else `DANGLING_COVERS_REF` (error); `covers:` never appears on a procedure — else `COVERS_ON_PROCEDURE` (error)

**Warnings** (do not fail the lint):
- `TERMINAL_SEND_STEP` — a scenario (or its terminal workflow) ends on a `send` step. A trailing send asserts nothing and the scenario will be reported `aborted` at run time; add a `validate` step after the send.
- `WEAK_SENSITIVE_CONTEXT_VAR` — a `ctx.var` marked sensitive resolves to a literal shorter than the value-net length floor (`< 5` chars). It is masked **by location** (ctx panel + injection paths) but is below the floor for the global value-net, so a server echo of it into an **undeclared** field would not be caught — declare that field in `sensitive_fields`.
- `UNKNOWN_KNOWLEDGE_FIELD` — a requirement (or knowledge file) carries a key outside the closed catalog; use a catalog field or move it under `more_details:`.
- `UNCOVERED_REQUIREMENT` — an in-scope requirement (owned-PG + DOM; installed-PG excluded) has no covering scenario/row/step. Add a `covers:` or record an explicit deferral; `syz rtm` shows the full gap list. **Suppressed in `--knowledge` mode** (see below).
- `PLACEHOLDER_KNOWLEDGE_CONTENT` — a requirement's `notes:` still carries the scaffold's example text. `notes:` is the only mandatory prose field, so an untouched example passes schema validation while recording no knowledge at all. The check matches the exact sentinel the scaffold writes — it is not a `TODO` heuristic — and stays a warning so a half-authored workspace remains lintable mid-session.
- `UNUSED_DOMAIN_AREA` — a `DOMAIN.yaml` `areas[].key` with no requirement or guideline bound to it. `UNKNOWN_DOMAIN_AREA` already catches a requirement naming an unregistered area; this catches the opposite drift — a registry entry nothing uses. Bind a requirement/guideline to it, or drop it from the registry.

Both of the above run in **every** mode, not just `--knowledge` — they are knowledge-layer rules, and gating them on the flag would let a placeholder survive a full pre-flight.

**What `--knowledge` mode changes.** Every shape rule above runs byte-identically — id grammar, layer/scope binding, duplicates, unknown fields, malformed entries — so a draft can never silently rot. Exactly one behaviour differs: `UNCOVERED_REQUIREMENT` is **suppressed**, because at requirements-writing time no scenarios exist and it would otherwise fire on every requirement and bury the findings that are actionable. The census line states the omission rather than hiding it. `DANGLING_COVERS_REF` remains an **error** (it is meaningful whenever scenarios do exist, and never fires spuriously when they do not), and `COVERS_INPROGRESS_REQUIREMENT` remains a warning.

All issues are collected in a single pass — no early exit. Exit 0 when all checks pass (warnings alone do not fail); exit 1 when any error is found. **A workspace with clean requirements and zero scenarios exits 0** — that is the guarantee `--knowledge` exists to provide.

### `syz rtm`

Generate the **Requirements Traceability Matrix** — a *derived* report (like `index.html` / `ledger.json`, never hand-maintained) joining the knowledge layer's requirements to the `covers:` references in your scenarios. Read-only.

```bash
syz rtm                       # write .syz/rtm.md (markdown matrix)
syz rtm --json                # write .syz/rtm.json instead
syz rtm --strict              # exit 1 if any in-scope requirement is uncovered or any covers: is dangling
syz rtm --lastrun             # annotate each covering locus with its latest-run outcome
syz rtm --json --strict --lastrun   # flags compose
```

| Flag | Description |
|---|---|
| _(none)_ | Write `.syz/rtm.md`: a two-column table (**Requirement** + **Covered by**) followed by `## Uncovered (N)` and `## Dangling covers: (N)` footers. Exit 0. |
| `--json` | Write `.syz/rtm.json` instead: `summary` (`total`/`covered`/`uncovered`/`orphans`), per-requirement `covered_by`, a `gaps` array (uncovered ids), and an `orphans` array (dangling refs). |
| `--strict` | The **only** flag that affects the exit code: exit 1 if any in-scope requirement is uncovered **or** any `covers:` is dangling. The CI gate. |
| `--lastrun` | Annotate each covering locus inline with its outcome from the latest run's `execution.json` — `(success)`/`(failure)`/… (a step uses its `StepOutcome`; a scenario/row uses its status; `not_run` for loci the latest run did not execute) — and append the aggregated counts `[success(n), …]` to the requirement. No exit-code effect. |

**Scope:** in-scope requirements = owned-plugin PG + all DOM (installed-plugin PG requirements are excluded — the publisher owns their coverage; installed plugins appear only as steps in DOM-covering scenarios). Load/parse errors exit 1, like `lint`.

### `syz init`

Create the `.syz/` project structure and write the knowledge layer + all AI tool context files.

```bash
syz init
```

Creates all missing `.syz/` subdirectories. Always overwrites the syz-owned knowledge docs (`dossier/SYZ-INDEX.md`, `SYZ-MANUAL.md`, `SYZ-GUIDELINES.md`, `SYZ-TESTING.md`, `SYZ-NOTICE.md`, `SYZ-MIGRATE.md`), the `CLAUDE.md` pointer files, `AGENTS.md` (the open `agents.md` cross-procedure standard — the canonical anchor), and all vendor-specific AI tool context files inside `.syz/` (Cursor, GitHub Copilot, Windsurf, Continue.dev, Amazon Q, JetBrains AI, Gemini Code Assist, Aider). Scaffolds the user-owned `dossier/DOMAIN.yaml` and `dossier/TEST-STRATEGY.md` **only if absent** — never overwrites them. Creates `.syz/ai-api.yaml` if absent (never overwrites — user-configurable). Never touches `README.md` files, `PLUGIN-GUIDE.yaml`, or any scenario/plugin/environment files. `syz init` is the only command that scaffolds `.syz/`; `run`/`install`/`generate`/`rtm` fail fast outside a workspace.

```bash
syz init --force   # create a nested workspace even inside an existing one (monorepo sub-workspace)
```

**Workspace resolution — a git-style upward walk.** Every command except `init` resolves the **workspace root** by walking up from the current directory to the **nearest ancestor** that contains a `.syz/` directory (exactly how `git` finds `.git/`). All paths are anchored to that resolved root, so `syz run`, `install`, `generate`, `lint`, and `rtm` work from **any subdirectory** — including from **inside `.syz/`** (where you open your AI tool) and its subfolders (e.g. `.syz/scenarios/e2e/`). Nearest wins, so a closer `.syz/` shadows one further up; there is no ceiling — the walk goes to the filesystem root. When no `.syz/` is found in the current directory or any parent, the command fails fast: `not a syz workspace — no .syz/ found in the current directory or any parent. Run 'syz init' …`.

`init` is the one exception — it is **cwd-only**: it scaffolds `.syz/` exactly in the current directory and never resolves upward. If the current directory already holds `.syz/`, `init` refreshes it (the sanctioned re-run). If instead a **parent** directory holds `.syz/` — i.e. you are in a subdirectory of an existing workspace — `init` **refuses** (`NESTED_SYZ_WORKSPACE`), naming the existing root, so you cannot silently create a second, shadowing workspace. Pass `--force` to override that guard for the deliberate nested/monorepo sub-workspace case.

Open `.syz/` as your AI tool's workspace root — it auto-discovers its context file and reads `dossier/SYZ-INDEX.md`, which routes to the rest of the knowledge layer. `.syz/AGENTS.md` is the **canonical cross-procedure anchor**: any tool that honours the open `agents.md` convention (Codex, Cursor, Aider, Gemini CLI, Zed, Jules, …) auto-discovers it with **no** vendor-specific emitter, so new tools work out of the box. The vendor-specific files (`CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, …) are kept for tools that don't yet read `AGENTS.md`. Because resolution is an upward walk, `syz` commands you run from inside that session resolve to the same workspace.

**Doc version-skew advisory.** Every SYZ-owned doc carries a `<!-- syz-version: X.Y.Z -->` stamp on line 1. When you upgrade the CLI but have not re-run `syz init`, `run`, `generate`, `lint`, `install`, and `rtm` print a **non-blocking** advisory — a concise one-liner before the command's output and a framed reminder after it (a *bookend*, so it is not lost in a long log). Both go to **stderr** (machine `--json` stdout stays clean), never throw, and never change an exit code. The remedy is always `syz init`, which refreshes the SYZ-owned docs while leaving your scenarios, plugins, `PLUGIN-GUIDE.yaml`, `dossier/DOMAIN.yaml`, and `dossier/TEST-STRATEGY.md` untouched. A `syz run` additionally records the skew in `execution.json` (`notices.doc_version_skew`) and surfaces it in `index.html` (skew badge + banner). Nothing is printed or recorded when the docs are in sync.

**Upgrade-available advisory.** Separately, `syz` checks whether a newer **stable** release has been published to npm; when your installed CLI is behind, `run`, `generate`, `lint`, `install`, and `rtm` print the same kind of non-blocking **bookend** — a one-line `a new syz release is available: vX → vY` before the output and a framed reminder after it, both on **stderr**. The remedy is `npm i -g syzs-cli@latest`. The check **never blocks** the command (the registry lookup runs in the background, so the advisory you see is from a prior run; the first run after install shows nothing), never points at a pre-release, and is **dormant in CI and when `SYZ_NO_UPDATE_CHECK` is set**. It self-clears the moment you upgrade. A `syz run` also records it in `execution.json` (`notices.upgrade_available`) and shows it in `index.html` (upgrade badge + banner). This is **distinct** from the doc version-skew advisory above: that one means your **docs** are older than your **CLI** (fix with `syz init`); this one means your **CLI** is older than the latest **published** release (fix with `npm i -g syzs-cli@latest`). *(Privacy: the background check makes a single unauthenticated request to the public npm registry — the same host `npm` itself contacts; set `SYZ_NO_UPDATE_CHECK` to disable it entirely.)*

Expanding a step shows each phase in full, with every structured/multi-line value pretty-printed in a readable code block (JSON re-indented; XML/YAML/text kept verbatim) — this applies to **all** phase bodies: **Input Resolution** (raw → resolved), **Context Variables** (before/after), **Payload Construction** (the rendered payload), **Executor** (the complete request sent and full response envelope received — status, headers, body, format, size, nothing elided, secrets masked), a failed **Assertion**'s expected/actual, and **Ledger Write** (the full ledger entry plus a highlighted list of the values this step wrote, `ledger.<key>.<field>`, that are now resolvable downstream). Short scalar values stay inline. Filter scenarios by name (search box) or by outcome via the **status dropdown** — six options (`All`, `Success`, `Failure`, `Error`, `Exception`, `Aborted`), each showing its live count; selecting one shows exactly the cards with that outcome (a zero-match filter shows a *no scenarios match* message, never a blank list). The headline stat cards stay two-bucket (`Total / Passed / Failed / Duration`). When a newer syz release is available on npm, the header likewise shows an amber upgrade badge (`cli vX → vY available`) and a banner pointing at `npm i -g syzs-cli@latest`. Start here. |
| `execution.json` | Run-level index: all scenarios with their pass/fail status. The container holds whichever apply and is omitted entirely when neither does. |
| `<scenario-path>/ledger.json` | Per-scenario: resolved inputs, response envelopes, assertion results. Most useful for "why did this not resolve the way I expected?" |
| `<scenario-path>/debug.log` | Per-scenario: phase-by-phase plain-text trace matching the terminal output exactly. |
| `junit.xml` | Only written when `--reporter junit` is set. Consumed by CI platforms natively. |

**First-line debug tool:** run `syz lint --env <name>` before opening artifacts. Lint catches missing procedures, broken ledger references, and unset environment variables without executing a single request.

### Debugging a failed assertion — where to look

When `syz run` exits 1 because a scenario reported `VALIDATION_FAILURE`, follow this path:

1. **Open `.syz/results/<run-id>/<scenario-path>/ledger.json`.** Find the validate-step entry — the one whose `outcome` is `"failure"`.
2. **Read `validation.checks[]`.** It contains one result per assertion in the validate procedure, in declaration order. Each result has:
   - `description` — the human label from the check
   - `passed` — `true` or `false`
   - `expected` — the value the check was comparing against (resolved from `value` or `value_from_input`)
   - `actual` — the value at the JSONPath / from `content` / from the response
   - `detail` — optional; populated for `matches_schema` violations (`"items[2].qty: expected type number, got string"`), `expression` errors, and `ai` reasoning
3. **Read `http.response.fields.body` (or `http.response.error`) and `http.request` on the upstream send step** to see exactly what was sent and received. Sensitive fields appear as `[REDACTED]` — but unredacted values are still used during assertion evaluation.
4. **For `expression` failures**, the `detail` field shows either the thrown error message or `"Expression must return a boolean, got <type>"`. Copy the expression from the procedure YAML, paste into a Node REPL with `response` and `inputs` set to the values from `ledger.json`, and reproduce locally.
5. **For `operator: ai` failures**, `detail` contains the AI's stated reasoning. If the verdict looks wrong, tighten the `instruction` — AI assertions are only as deterministic as their prompt.

The same artifact (`ledger.json`) is the source of truth for `index.html` — anything visible in the HTML report can be traced back to a field on a ledger entry.

### Common errors

| Error code | What it means | First thing to check |
|---|---|---|
| `LEDGER_REFERENCE_ERROR` | A `{{ ledger.x.y }}` expression references a procedure or path that does not exist in the ledger at that point in the flow | Confirm the procedure ran earlier in the flow; check the JSONPath against `ledger.json` |
| `UNRESOLVED_TEMPLATE` | One or more `{{ }}` expressions remain unresolved after Phase 1 resolution | The error points at the exact procedure source file and, per field, the field path, its value, the unresolved `{{ }}` expression(s), and the `file:line` — go straight there and check the reference names a real data / env / ledger / ctx / plugin source. Run `syz lint` to list every unresolved reference at once |
| `PROCEDURE_NOT_FOUND` | The procedure name in the scenario flow does not match any procedure in a loaded plugin | Verify the plugin is installed (`dependency.json` or `.syz/plugins/`) and the procedure name is spelled correctly |
| `VALIDATION_FAILURE` | One or more assertion checks failed | Open `ledger.json` and compare the actual response against the expected values in the failing `checks` |
| `EXECUTION_ERROR` | An executor could not be set up for a send (e.g. no `execution_library` declared). Network-layer failures are **not** this — a refused connection or timeout is captured as `$.error` data and the run continues | Confirm the send procedure declares `execution_library: http`. For network failures, assert on `$.error.code` in a validate step |
| `AI_CONFIG_NOT_FOUND` | `.syz/ai-api.yaml` is missing | Run `syz init` to create the file, then configure it |
| `AI_CONFIG_INCOMPLETE` | `ai-api.yaml` exists but `base_url`, `model`, or `api_key` is empty after `{{ os-env-var:NAME }}` resolution | Open `.syz/ai-api.yaml` and fill in (or set env vars for) the listed empty fields |
| `SCENARIO_SCHEMA` | A scenario YAML file fails schema validation | Check the Zod error output — it names the failing field and expected type; compare against the scenario format above |
| `PLUGIN_MANIFEST_SCHEMA` | A `plugin.yaml` fails schema validation (e.g. missing `version`) | Open the named `plugin.yaml` and confirm it has `plugin: <name>` and `version: "<semver>"` |
| `PROCEDURE_DEFINITION_SCHEMA` | An `procedures/<file>.yaml` fails schema validation (e.g. invalid `type`, missing `name`) | Open the named procedure file and confirm `name`, `type` (`send`/`validate`/`workflow`/`craft`), and any `crafter`/`execution_library` declarations are correct |
| `ENV_CONFIG_SCHEMA` | An environment YAML (`.syz/environments/<env>.yaml`) fails schema validation | The top-level `name:` field is required; unknown extra keys are accepted silently — the error names the specific failing field |
| `AI_CONFIG_SCHEMA` | `.syz/ai-api.yaml` fails schema validation (e.g. `ai:` block missing or wrong shape) | Confirm the file has an `ai:` block with `base_url`, `model`, `api_key` (use `{{ os-env-var:NAME }}` for env-backed values) |
| `UNSUPPORTED_EXECUTOR_TYPE` | A send procedure declares an `execution_library` value that is not registered (only `http` is supported today) | Set `execution_library: http` in the procedure YAML; non-HTTP transports arrive in a future phase |
| `MISSING_CONNECTION` | A `send` step whose procedure uses a stateful executor has no `connection` field | Add `connection: <handle>` naming a `connections` block declared in the env or scenario |
| `UNKNOWN_CONNECTION` | A step's `connection` names a handle that no `connections` block (env or scenario) declares | Declare the handle under `connections:`, or fix the name to match an existing handle |
| `CONNECTION_EXECUTOR_MISMATCH` | A handle's `execution_library` differs from the procedure's executor | Make the handle's `execution_library` match the procedure, or point the step at a handle for the right executor |
| `KEEP_ALIVE_ON_STATELESS_EXECUTOR` | A handle with `lifecycle: keep_alive` targets a stateless executor such as `http` | Drop `lifecycle: keep_alive` (stateless steps are always ephemeral) — `keep_alive` is only meaningful for stateful executors that hold a connection across steps |
| `CONNECTION_OVERRIDE_EXECUTION_LIBRARY` | A step's `connection_overrides` sets `execution_library` | Remove `execution_library` from `connection_overrides` — overrides tune connection fields for a negative test but a handle is bound to one executor for its life |
| `LITERAL_CREDENTIAL_IN_CONNECTION` | A secret-named field (password, token, api_key, …) in a committed connection block (procedure block or scenario `connections`) carries a literal value | Route the secret through `{{ os-env-var:NAME }}` — connection blocks ship in plugins/scenarios and must stay secret-free |
| `TRANSACTION_REQUIRES_KEEP_ALIVE` | A transactional `inputs.operation` (`begin`/`commit`/`rollback`/`abort`/`exec`/`discard`) names a handle whose lifecycle is not `keep_alive` | Set `lifecycle: keep_alive` on the handle — an ephemeral connection cannot span a transaction |
| `NO_LIVE_CONNECTION` | (runtime, `$.error.code`) A `keep_alive` handle failed to open earlier and is now a dead marker; a later step naming it does not retry | Captured as `body.error` data — fix the connect failure on the *first* step that opened the handle (its `body.error` carries the native cause) |
| `AI_RESPONSE_INVALID` | An AI feature (`{{ ai: ... }}` resolver, `crafter: ai`, or `operator: ai`) ran but the AI provider's response was unusable — truncated, content-filtered, or empty | The error names the offending `ai-api.yaml` field (e.g. `max_tokens`); adjust it. Or check the model, base_url, or instruction phrasing |
| `PLUGIN_CREATION_TERMINATED` | `syz generate plugin` was interrupted before the interactive walkthrough completed (EOF, SIGINT, or signal) | Re-run with all required answers, or pass `--from openapi:<path>` / `--from postman:<path>` to skip the walkthrough |
| `INCOMPATIBLE_GUIDE_ONLY_FLAGS` | `--guide-only` was combined with `--from`, `--force`, or `--overwrite` — a guide-first shell is spec-less and never overwrites | Drop the named flag, or drop `--guide-only` to generate from a source |
| `PLUGIN_FOLDER_EXISTS` | `--guide-only` targets a `.syz/plugins/<name>/` folder that already exists (guide-only only ever creates a fresh shell) | Use a different `--name`, or edit the existing `PLUGIN-GUIDE.yaml` directly |

## Resolver reference cheat sheet

All `{{ }}` expressions use the same syntax everywhere: scenario inputs, workflow wiring, validate checks, and procedure defaults.

| Expression | Resolves From | Example |
|---|---|---|
| `{{ ledger.<procedure>.<path> }}` | Execution ledger — JSONPath into ledger entry | `{{ ledger.payments.send_order.http.response.fields.body.orderId }}` |
| `{{ ledger.<procedure>.outputs.<field> }}` | Manifest output shortcuts | `{{ ledger.payments.send_order.outputs.orderId }}` |
| `{{ env.<plugin>.<field> }}` | Environment config | `{{ env.payments.base_url }}` |
| `{{ <plugin>.data.<field> }}` | Plugin shared data.yaml | `{{ payments.data.send_order.body.amount }}` |
| `{{ outline.<field> }}` | Current outline example row | `{{ outline.expected_status }}` (outline scenarios only) |
| `{{ inputs.<field> }}` | Current step's resolved inputs (post-Phase-1) — only available in fields rendered AFTER input resolution, e.g. craft `output_to_file` | `{{ inputs.orderId }}` |
| `{{ ai: <instruction> }}` | AI API — returns resolved value (non-deterministic; egresses to your provider — see `SYZ-NOTICE.md`) | `{{ ai: generate a random valid UUID }}` |
| `{{ os-env-var:NAME }}` | OS environment variable — `process.env[NAME]`. Load time (env files, `ai-api.yaml`) **and** runtime (scenario / plugin / data / template). Inline-capable. Every resolved value is masked as a secret. Unset → literal preserved | `"Bearer {{ os-env-var:USER_TOKEN }}"` |

**`os-env-var` is special:** it is the one prefix with the same meaning in every layer (always `process.env[NAME]`), so it resolves identically at load time and runtime. `ai:` and `os-env-var:` are colon-prefixed (a literal argument follows); the others are dot-prefixed key paths. `ledger`, `env`, `ai`, `outline`, and `os-env-var` are reserved and cannot be used as plugin names.

**Ledger repeated-procedure indexing:** When the same procedure runs more than once in a flow, the first run has no index; subsequent runs are 1-indexed. A **bare** reference (no `[n]`) resolves to the **latest** write; an explicit `[n]` addresses a specific historical run:
```
{{ ledger.payments.send_order.http.response }}      ← latest run (most recent write)
{{ ledger.payments.send_order[1].http.response }}   ← the second run specifically
{{ ledger.payments.send_order[2].http.response }}   ← the third run specifically
```
This "bare = latest" rule is what lets a polled workflow (`poll:`) re-run a send each attempt and have the same `validate` reference read **that attempt's** fresh response rather than the first attempt's.

**Cross-prefix references — any prefix can reference any other:**

A resolved `{{ }}` value that itself contains `{{ }}` is resolved again (recursively, up to depth 80, with cycle detection). The inner expression can use a *different* prefix than the outer one, so any direction works: env↔ledger, env↔data, ledger↔data, data→env, outline→data, etc.

```yaml
# env config — env value pointing at plugin data
payments:
  token: "{{ env.shared.api_key }}"                              # env → env
  default_currency: "{{ payments.data.currencies.default }}"     # env → data

# plugin data.yaml — data value pointing at env
send_order:
  body:
    callbackUrl: "{{ env.payments.base_url }}/callback"          # data → env

# scenario inputs — chained through ledger
inputs:
  parent_order: "{{ ledger.payments.send_create_parent.outputs.orderId }}"  # input → ledger
```

**Temporal caveat for ledger refs:** `{{ ledger.<procedure>.… }}` resolves against the *current* ledger state. A field that embeds a ledger ref (env, data, or another ledger value) only resolves cleanly if the producing step has already run earlier in the same scenario. Static-side chains (env↔data, ledger→env, ledger→data) are always safe.
