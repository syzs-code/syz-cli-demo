# SYZYGY — Knowledge Index (router)

This is the **entry point** to the SYZYGY knowledge layer. It routes you to the right document — it does not duplicate their content. Read the doc a task points you to *before* doing the task.

> **Version check — do this first.** These docs were generated by syz `0.8.0` (the `syz-version` stamp on line 1 of every `SYZ-*` doc). If `syz --version` reports a **different** version, the CLI has been upgraded but this knowledge layer has **not** — treat these docs as **possibly stale**, do not rely on them, and ask the user to run `syz init` to refresh the SYZ-owned docs before authoring or running anything.

## Ownership convention — the `SYZ-` prefix is the contract

| Class | Marker | Lifecycle |
|---|---|---|
| **syz-owned** | `SYZ-` filename prefix | Generated by `syz init`, version-headed, **always overwritten** on every `syz init`. Never edit — your changes are lost on the next upgrade. |
| **user-owned** | no `SYZ-` prefix | Scaffolded **only if absent**, then **never overwritten by any `syz` command — including `--force`**. This is where your knowledge lives. |

The five `SYZ-*.md` docs below are owned. `DOMAIN.yaml`, `TEST-STRATEGY.md`, and each plugin's `PLUGIN-GUIDE.yaml` are yours.

## Document map

| Document | Read it for |
|---|---|
| `SYZ-MANUAL.md` | The full CLI reference — every command, flag, file format, directory structure, resolver, and assertion operator. The "how is this written?" lookup. |
| `SYZ-GUIDELINES.md` | What SYZYGY is, the mental model, and design best-practices — agent types, authoring patterns, precedence, CI, choosing operators. The "how should I approach this?" guidance. |
| `SYZ-TESTING.md` | Test-level how-to and the **agent scenario-authoring workflow** — discover the contract, author, `syz lint`, fix, run. Read this before writing any scenario. |
| `SYZ-NOTICE.md` | Risk, privacy & responsibility — AI non-determinism + mandatory human review, data egress, execution safety, the no-warranty posture, and the anti-hallucination directive. Read it once before using AI features or running against shared infra. |
| `DOMAIN.yaml` *(yours)* | Cross-integration business knowledge as schema'd, lint-validated YAML — an `areas:` registry, `entities:`, and ID'd `requirements:` (`REQ-<AREA>-DOM-<NNN>`) for what "correct" means end-to-end. Domain language, no syz vocabulary. |
| `TEST-STRATEGY.md` *(yours)* | Your team's test phases, levels, and coverage intent. |
| `.syz/plugins/<name>/PLUGIN-GUIDE.yaml` *(yours)* | One integration's behaviour as schema'd, lint-validated YAML `requirements:` (`REQ-<PLUGIN>-PG-<NNN>`) — rules, inputs, errors. Every plugin folder under `.syz/plugins/` and `.syz/plugins.installed/` carries one. |

## Directive routing table — read X before doing Y

| Before you… | You MUST read |
|---|---|
| **author or edit a scenario** | `SYZ-TESTING.md`, `DOMAIN.yaml`, `TEST-STRATEGY.md`, **and** the `PLUGIN-GUIDE.yaml` of every plugin the scenario uses |
| **hand-author or customise a plugin** | `SYZ-MANUAL.md` (plugin/agent/format reference) **and** `SYZ-GUIDELINES.md` (design guidance), then write/update that plugin's `PLUGIN-GUIDE.yaml` |
| **look up a command, flag, file format, or operator** | `SYZ-MANUAL.md` |
| **decide an approach** (which agent type, which operator, how to structure a flow) | `SYZ-GUIDELINES.md` |
| **understand what the system under test should do** | `DOMAIN.yaml` and the relevant `PLUGIN-GUIDE.yaml` |
| **capture requirements / check what is already covered** | `DOMAIN.yaml` + `PLUGIN-GUIDE.yaml` (the read-first corpus) and `syz rtm` (the derived traceability matrix); link tests with `covers:` — see `SYZ-TESTING.md` |
| **use an AI feature (`{{ ai: }}` / `operator: ai`) or run against shared/live infra** | `SYZ-NOTICE.md` |

Plugin-guide discovery is a **pattern, not a list**: every plugin folder under `.syz/plugins/` and `.syz/plugins.installed/` carries a `PLUGIN-GUIDE.yaml` — open the relevant one before authoring its tests. This stays correct as plugins are added and removed.
