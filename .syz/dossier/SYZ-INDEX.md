# SYZYGY — Knowledge Index (router)

This is the **entry point** to the SYZYGY knowledge layer. It routes you to the right document — it does not duplicate their content. Read the doc a task points you to *before* doing the task.

> **Version check — do this first.** These docs were generated by syz `0.10.5` (the `syz-version` stamp on line 1 of every `SYZ-*` doc). If `syz --version` reports a **different** version, the CLI has been upgraded but this knowledge layer has **not** — treat these docs as **possibly stale**, do not rely on them, and ask the user to run `syz init` to refresh the SYZ-owned docs before authoring or running anything.

## Binding interaction contract — always in force

These rules bind every agent working in this workspace, on every task:

1. **Identify the user's goal before touching any file.** If the request is plain-language, ambiguous, or the user seems new to syz, read `SYZ-PLAYBOOK.md` and triage the intent there.
2. **Ask, never guess.** When a plugin, scenario, environment, or any other specific is unnamed or uncertain, list what exists in `.syz/` and ask the user.
3. **Knowledge lives only inside `.syz/`.** Never search for or infer knowledge outside `.syz/` on your own initiative — not parent folders, not the application's source code, not the user's other directories. A missing user-owned file means *scaffold it or ask* — never hunt. The only exception is a location the **user explicitly points to** (a spec path passed to `--from`, existing tests supplied for migration).
4. **You operate, the human answers.** Run the `syz` commands yourself; the human supplies knowledge and decisions. Narrate in plain language what was / is / will be done; use syz vocabulary only with users who demonstrate it.
5. **Never invent capability.** If syz lacks an operator, flag, field, or syntax a task needs, stop and state exactly what is missing (see the anti-hallucination directive in `SYZ-NOTICE.md`).

## Ownership convention — the `SYZ-` prefix is the contract

| Class | Marker | Lifecycle |
|---|---|---|
| **syz-owned** | `SYZ-` filename prefix | Generated by `syz init`, version-headed, **always overwritten** on every `syz init`. Never edit — your changes are lost on the next upgrade. |
| **user-owned** | no `SYZ-` prefix | Scaffolded **only if absent**, then **never overwritten by any `syz` command — including `--force`**. This is where your knowledge lives. |

The seven `SYZ-*.md` docs below are owned. `DOMAIN.yaml`, `TEST-STRATEGY.md`, and each plugin's `PLUGIN-GUIDE.yaml` are yours.

## Directive routing table — read X before doing Y

| Before you… | You MUST read |
|---|---|
| **figure out what the user actually wants** — the request is plain-language, the goal is ambiguous, or the user is new to syz | `SYZ-PLAYBOOK.md` — triage the intent there, then follow its activity playbook |
| **author or edit a scenario** | `SYZ-TESTING.md`, `DOMAIN.yaml`, `TEST-STRATEGY.md`, **and** the `PLUGIN-GUIDE.yaml` of every plugin the scenario uses — **and obey every applicable `guidelines:` entry** in those files |
| **construct or edit a procedure / a request, or choose or configure an executor** | the `guidelines:` of the relevant `PLUGIN-GUIDE.yaml` **and** `DOMAIN.yaml` — these are **binding**: a guideline like "requests must include header X" or "must use the http executor" is a rule you MUST apply, not advice. Drop a `# see GL-…` comment where you implement it. |
| **hand-author or customise a plugin** | `SYZ-MANUAL.md` (plugin/procedure/format reference) **and** `SYZ-GUIDELINES.md` (design guidance), then write/update that plugin's `PLUGIN-GUIDE.yaml` — including any `guidelines:` it needs |
| **look up a command, flag, file format, or operator** | `SYZ-MANUAL.md` |
| **decide an approach** (which procedure type, which operator, how to structure a flow) | `SYZ-GUIDELINES.md` |
| **understand what the system under test should do** | `DOMAIN.yaml` and the relevant `PLUGIN-GUIDE.yaml` |
| **capture requirements / check what is already covered** | `DOMAIN.yaml` + `PLUGIN-GUIDE.yaml` (the read-first corpus) and `syz rtm` (the derived traceability matrix); link tests with `covers:` — see `SYZ-TESTING.md` |
| **use an AI feature (`{{ ai: }}` / `operator: ai`) or run against shared/live infra** | `SYZ-NOTICE.md` |
| **migrate a team's existing tests into this workspace** (and *only* then) | `SYZ-MIGRATE.md` — load it **if-and-only-if** the task is migrating existing tests; **never** load it while authoring net-new tests, running `generate`/`run`, or any other flow (those keep routing to `SYZ-TESTING.md` / `SYZ-GUIDELINES.md`). Migration forbids originating behaviour from specs; authoring permits it — keep the two apart. |

Plugin-guide discovery is a **pattern, not a list**: every plugin folder under `.syz/plugins/` and `.syz/plugins.installed/` carries a `PLUGIN-GUIDE.yaml` — open the relevant one before authoring its tests. This stays correct as plugins are added and removed.
