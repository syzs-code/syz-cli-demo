# SYZYGY — Risk, Privacy & Responsibility Notice

This document tells you what to watch for when using SYZYGY: what **real systems** your tests touch, where data **leaves your machine**, and where **responsibility** sits. It is informational — it does not change how any command behaves. Use of the `syz` CLI is governed by the `LICENSE` (EULA) at the repository root.

## Execution is deterministic — `syz run` makes no model calls

`syz run` contains **no AI**. Every value in a run comes from a committed file or a prior step's recorded output, so the same scenario against an unchanged system produces the same request and the same verdict every time. There is no resolver, operator, or crafter that reaches a language model.

AI belongs at **authoring** time. Your coding assistant reads this dossier and writes a concrete artefact once — a `data.yaml` entry, a nunjucks template, a regex assertion — and you review and commit it. The runtime only replays what you committed, which is what makes a run reproducible and auditable.

## Data egress & privacy

`syz` sends **only** the requests your scenarios and plugins describe, to the targets your environment config names. Nothing else leaves your machine: no telemetry, no model provider, no third party. The ledger, reports, and debug log are written locally.

- Keep credentials in `{{ os-env-var:NAME }}` rather than literals, so they are masked everywhere they could otherwise surface (errors, traces, debug log, reports).
- Anything you put in a scenario, template, or `data.yaml` may be sent to the system under test. Point environments at the right target before you run.

## Execution safety — tests hit real systems

`syz run` performs the **real** calls your scenarios and plugins describe — live HTTP requests today, and (Phase 2) real Kafka/RabbitMQ/SFTP/database/object-store operations. There is no built-in sandbox.

- Point environments at the **right** target. A scenario run against production *is* a production action.
- Negative and destructive tests do real work — review what a scenario does before running it against shared or live infrastructure.

## Anti-hallucination directive (for the authoring agent)

When authoring plugins or scenarios, **never invent a capability that SYZYGY does not have.** If a test needs an operator, flag, field, resolver prefix, executor, or syntax that does not exist in `SYZ-MANUAL.md`, **stop and say so** — state the specific missing capability and why the test cannot be authored as asked — rather than fabricating one that "looks right." A fabricated construct does not silently pass: `syz lint` rejects unknown schema/identifiers (`UNKNOWN_*`, and the reserved-`syz` / unknown-`ctx.var` checks), so an invented field fails loudly later. Self-reporting the gap up front is faster and honest; do not paper over a missing feature.
