# SYZYGY — Test Authoring

How to take a test from idea to a passing run, and the workflow an AI coding agent follows to author scenarios deterministically. For exact formats see `SYZ-MANUAL.md`; for design guidance see `SYZ-GUIDELINES.md`.

## Authoring a test case

From zero to a passing test in five steps.

1. **Initialise the project:**

   ```bash
   syz init
   ```

   `syz init` is the **only** command that scaffolds `.syz/` and writes the syz-owned knowledge layer (`dossier/SYZ-*.md`, the `CLAUDE.md` pointers, the AI-tool context files). Run it first. `run`, `install`, and `generate` operate **inside** a workspace and fail fast when `.syz/` is absent — `not a syz workspace — run 'syz init'` (the same model as `git` outside a repository). Re-running `syz init` re-writes the syz-owned files to the current CLI version; it never touches your plugins, scenarios, environments, or your user-owned `DOMAIN.yaml` / `TEST-STRATEGY.md` / `PLUGIN-GUIDE.yaml`.

2. **Acquire a plugin** — choose one approach:

   - **Shared plugin from git:** `syz install https://github.com/<org>/<repo>.git@<version> --plugin <name>`
   - **Generated from an OpenAPI spec or Postman collection:** `syz generate plugin --name <name> --from openapi:<path/to/spec.yaml>`
   - **Hand-authored (for plugin owners):** see *Plugins — using and customising* in `SYZ-MANUAL.md`.

3. **Write a scenario** in `.syz/scenarios/<level>/<name>.yaml`:

   ```yaml
   name: "Smoke — successful <your_operation>"
   level: component
   environment: local
   plugins:
     - name: <your-plugin>
       version: "1.0.0"

   flow:
     - type: send
       agent: <your-plugin>.step_<your_operation>
       inputs: {}

     - type: validate
       agent: <your-plugin>.validate_<your_operation>
       inputs:
         response:        "{{ ledger.<your-plugin>.step_<your_operation>.http.response }}"
         expected_status: 200
   ```

4. **Pre-flight check:**

   ```bash
   syz lint --env local
   ```

   All errors are reported in a single pass — fix them before proceeding.

5. **Run and review:**

   ```bash
   syz run --suite .syz/scenarios/ --env local
   ```

   Open `.syz/results/<run-id>/index.html` to see per-step results, resolved inputs, and assertion outcomes. Use the status dropdown to filter cards by a single outcome (`Success` / `Failure` / `Error` / `Exception` / `Aborted`, each with a live count) when triaging a mixed run.

## Scenario levels

`level:` is a free-form string. SYZYGY uses it only as metadata for filtering and reporting. Common conventions — matching the folders under `.syz/scenarios/`:

| Convention | Meaning |
|---|---|
| `component` | Single service, mocked dependencies |
| `integration` | Multiple real services |
| `e2e` | Full end-to-end through the stack |
| `uat` | User-acceptance, near-production environment |

SYZYGY does not enforce these values — use whatever names your organisation already uses. Record the phases and levels your team actually uses, and the coverage you expect at each, in `TEST-STRATEGY.md` (it is yours — `syz init` scaffolds a stub and never overwrites it).

## Waiting on async behaviour

When a scenario touches something **asynchronous or eventually consistent** (a queue consumer catching up, an object landing in a bucket, a downstream settling), do not reach for a fixed sleep by default. A guessed delay is the classic source of flaky tests.

- To wait **until the system reaches a state**, author a polled workflow — a `workflow` step with a `poll:` block (`SYZ-MANUAL.md` → *poll:*). It re-runs until its validate converges or a bound trips: fast when the system is fast, patient up to the bound, deterministic either way.
- Use the built-in `syz.wait` (`SYZ-MANUAL.md` → *Fixed delay*) **only for a genuinely fixed window** that is itself part of the contract — a rate-limit window, a TTL/cache expiry, a token valid at +N seconds. The duration is the thing under test, not a guess.

See `SYZ-GUIDELINES.md` → *Waiting on async behaviour* for the full decision. Rule of thumb: if you are tempted to *increase* a `syz.wait` because the test flaps, convert it to a `poll:`.

## Owned vs installed plugins

A scenario does not care whether the plugin it references is **owned** (hand-authored under `.syz/plugins/<name>/`, committed with your repo) or **installed** (pulled from git under `.syz/plugins.installed/<name>/`, gitignored). The agent FQN (`<plugin>.<agent>`) resolves against both locations identically.

- **Owned plugins** are your team's own integrations. You evolve them alongside the scenarios that use them; their `PLUGIN-GUIDE.yaml` is yours to write and keep current.
- **Installed plugins** are version-pinned in `dependency.json` and restored by `syz install`. Their `PLUGIN-GUIDE.yaml` ships *with* the plugin (the publisher's integration knowledge) — read it, but do not edit the installed copy; it tracks the source and is overwritten on the next install.

When the same integration is referenced by many scenarios, prefer an installed, versioned plugin so every consumer pins a known-good contract.

## Agent scenario-authoring workflow

This is how an AI coding assistant "auto-writes test scenarios by following the guidelines" — deterministically, with **no in-process AI call inside `syz`**. The agent reads the knowledge layer, writes YAML, and closes the loop on `syz lint`. The framework stays deterministic; the reasoning happens in the agent, not the runtime.

**1 — Discover the contract.** Before writing a line of scenario YAML, load:
- the relevant plugin's **`PLUGIN-GUIDE.yaml`** (`.syz/plugins/<name>/` or `.syz/plugins.installed/<name>/`) — the integration's **ID'd requirements** (`REQ-<PLUGIN>-PG-<NNN>`): what it does, its rules, inputs, and error semantics;
- **`DOMAIN.yaml`** — cross-integration **requirements** (`REQ-<AREA>-DOM-<NNN>`) and what "correct" means end-to-end;
- **`TEST-STRATEGY.md`** — the team's phases, levels, and coverage intent;
- the agent FQNs available — every `agents/<name>.yaml` under the plugin (`send` / `validate` / `craft` / `workflow`);
- the **current coverage** — run `syz rtm` and read `.syz/rtm.md` to see which requirements are already covered and which are gaps, so you neither duplicate an existing test nor miss an uncovered requirement.

The requirement files say **what to test** (you never invent requirements); the agents say **how to wire it**. Map requirement → agents → scenarios at this step.

**2 — Cover the scope, exhaustively.** Before authoring any single scenario, settle *what the full set of tests must cover* — then commit to covering all of it. Coverage is **exhaustive within the scope of the request, never absolute**: if the user scopes the work (one operation, one area, one named scenario), exhaust exactly that scope; if the request is unscoped ("write tests for plugin `<x>`"), the scope is the whole plugin and the floor is its full **send-agent set**. Never silently narrow *below* what was asked, and never report the task done while it is quietly partial.

- **The floor is the send-agent set.** Send agents (`agents/step_*.yaml`, `type: send`) are plugin-owned, durable, and each is an integration operation worth asserting — so "every send agent in scope has ≥1 authored test" is the coverage floor. A **workflow counts toward the floor only when it encodes a distinct functionality** (a real multi-step business flow — acquire-token → create → verify → delete, or a capture-chained sequence); the thin generated `<agent>_send_success` wrappers are machinery for asserting one send worked, not functionalities, and do **not** add to the floor. **Validate and craft agents are never coverage targets** — they are assertion / request-building machinery, exercised transitively whenever the send or workflow they serve is covered.
- **The generated samples are your checklist, not your home.** `syz generate` writes one `sample_<slug>.yaml` per operation into `.syz/scenarios/generated/<plugin>/` and **clears and rewrites that folder** on every re-generation. Treat the sample set as the ready-made *checklist mirror* of the send-agent floor: **promote** each into `.syz/scenarios/<level>/` and author there — never harden a sample in place, since the next `syz generate` would wipe your edits.

Apply four directives:

1. **Floor, not menu.** Within the requested scope, every send agent — and every workflow that encodes a distinct functionality — gets ≥1 authored test *or* an **explicit deferral with a reason**. The sample set is the checklist; promote, don't edit in place.
2. **Friction is never a reason to skip.** Multipart/form bodies, capture-chained flows (`set:` → `ctx.var`), and operations whose `data.yaml` ships empty are *high-value* tests — the wiring cost is the point, not an excuse to drop them.
3. **Bias toward the awkward corners.** Lean *into* the risky, side-effecting, "probably-fine" operations — that is where defects hide — not toward the endpoints most likely to pass green.
4. **Open with a coverage ledger.** Start the deliverable with a short ledger — *M of N (in scope) covered* — and name every deferral and why. A partial result must be self-disclosing, never silently incomplete.

**Coverage is requirement-based.** The durable floor is **every in-scope requirement** (owned-plugin PG + all DOM; installed-plugin PG requirements are *never* component-tested — the publisher owns them, and they appear only as steps inside DOM-covering scenarios). Achieve it by **smart consolidation, not 1:1** — group by technique (input-validation → one outline; idempotency → its own double-send flow; lifecycle → a `ctx.var` state chain), and cover an extra requirement by adding one example row or one step. Link each test to the requirements it discharges with **`covers:`** (see *Requirement coverage* in `SYZ-MANUAL.md`); `syz rtm` then derives the matrix and `syz lint` warns on any `UNCOVERED_REQUIREMENT`. The send-agent floor below is the *mechanical* checklist that operationalises this — every covered requirement is exercised through some send agent or workflow.

**3 — Author per the current contract.** Write the scenario (or outline) using the formats in `SYZ-MANUAL.md`: pick the right agents, wire send responses into validate steps via `{{ ledger.<agent>.http.response }}`, choose operators per `SYZ-GUIDELINES.md`, and never end a flow on a `send` (always follow it with a `validate`). **Prefer the bundled `<slug>_send_success` workflow** to express a healthy send: to send a request and assert it merely succeeded (no transport/protocol error), use the generated `<plugin>.<slug>_send_success` **workflow** step rather than hand-writing a `send <plugin>.step_<slug>` + `validate <plugin>.validate_send_no_error` pair — it is the single-sourced "did the send work?" gate `syz generate` ships per send agent, so you neither re-derive nor mis-wire it. Layer business assertions **after** it as following `validate` steps reading `{{ ledger.<plugin>.step_<slug>.http.response }}` — the workflow's inner send writes that exact ledger key, so business validates wire up identically to the standalone-send case. **Carve-out:** hand-write the explicit `send` + `validate_send_no_error` (or a bespoke validate) only when the test asserts **on the send's `body.error` itself** — a negative-path test that *expects* a transport/protocol error and inspects its `code`/`message`; there the no-error gate is the wrong assertion and the explicit send is required to reach the error envelope. Keep secrets in `{{ os-env-var:NAME }}`, identity in `connections` handles or `{{ env.* }}` references — never literal credentials. When a value must be **captured from one step and reused later** — most commonly a generated agent's `{{ ctx.var.<param> }}` **path parameter** — wire its source with a `set:` block on the producing step (see *Context variables* in `SYZ-MANUAL.md` / `SYZ-GUIDELINES.md`); an unwired `ctx.var` read fails lint with `UNKNOWN_CONTEXT_VAR`. **Tag the scenario** as you write it — a broad `tags: [smoke, <area>]` at the top, refining a single outline row with a row-level `tags:` only when one example deserves its own slice — so the test joins the team's tag vocabulary from day one (see *Selecting a subset* in `SYZ-MANUAL.md`). **Set `covers:`** to the requirement id(s) the test discharges — at the scenario level for a whole-scenario requirement, on an example row or a flow step for finer linkage (it is distinct from `tags:` and never goes on an agent). This is what makes the test count toward the coverage floor and appear in `syz rtm`. **Test each unit with depth, not just a happy path:** apply the relevant *General test case design techniques* in `SYZ-GUIDELINES.md` — equivalence partitioning, boundary-value analysis, decision-table, pairwise, negative/error-guessing, state-transition, user-flow — selected by the shape of the unit under test (this is the depth complement to step 2's breadth). **Never invent capability:** if a test needs an operator, flag, field, resolver, or syntax that is not in `SYZ-MANUAL.md`, stop and state the specific missing capability and why the test cannot be authored — do not fabricate one (`syz lint` rejects it anyway; see *Anti-hallucination directive* in `SYZ-NOTICE.md`).

**4 — Lint (machine-readable).** Run:

```bash
syz lint --env <name> --json
```

`--json` emits the structured issue list — `{ issues: [{ severity, category, file, message, hint? }], errorCount, warningCount }` — so the agent parses results instead of scraping terminal text. The exit code is unchanged (1 if any `error`, else 0).

**5 — Fix and re-lint.** For each `error`, open the named `file`, apply the fix the `message`/`hint` describes, and re-run `syz lint --env <name> --json`. Repeat until `errorCount` is 0. Treat `warning`s (e.g. `TERMINAL_SEND_STEP`) as advisory but address them when they indicate a real authoring gap.

**6 — Run and review.** Once lint is clean:

```bash
syz run --suite .syz/scenarios/ --env <name>
```

To iterate on just the rows you are authoring, narrow with the same selectors lint understands — `--tag <list>`, `--example <list>`, or a `--suite .syz/suites/<name>.suite.yaml` manifest. Run `syz lint` with those flags first to confirm it previews exactly the rows the run will execute (a typo'd tag or example name surfaces there, before the run). Inspect `.syz/results/<run-id>/index.html` (or `ledger.json` for the structured truth) to confirm the scenario asserts what the contract requires. If a validate fails, the *test* may be right and the system wrong — confirm against `PLUGIN-GUIDE.yaml` / `DOMAIN.yaml` before "fixing" the assertion.

**7 — Confirm coverage.** Once the run is green, regenerate the matrix and check for gaps:

```bash
syz rtm --strict        # exit 1 if any in-scope requirement is uncovered or any covers: is dangling
syz rtm --lastrun       # annotate the matrix with each locus's latest-run outcome
```

A clean `syz rtm --strict` (exit 0) is the deterministic signal that the requirement floor is met. Wire it into CI alongside `syz lint`.

This write → `lint --json` → fix → run → `rtm` loop is the whole authoring contract. The knowledge layer (`PLUGIN-GUIDE.yaml` / `DOMAIN.yaml` / `TEST-STRATEGY.md` / the `SYZ-*` docs) supplies the *what*; `syz lint --json` and `syz rtm` supply the deterministic *is-it-correct* and *is-it-covered* signals.
