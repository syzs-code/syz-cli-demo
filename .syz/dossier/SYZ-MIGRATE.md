# SYZ-MIGRATE — Migrating Existing Tests into a `.syz` Workspace

> **When to read this.** Read this document **only** when your task is to migrate a team's
> **existing tests** into SYZYGY. `SYZ-INDEX.md` routes you here **if-and-only-if** that is the
> task. If you are instead authoring **net-new** tests from specs, requirements, or docs, this
> is the **wrong** document — stop and follow `SYZ-TESTING.md` / `SYZ-GUIDELINES.md` instead.
> Migrating existing tests and authoring new ones are different jobs with different rules, and
> this document's rules (which forbid originating behaviour from specs) must never leak into
> authoring.

> **Purpose.** Steer the migration of a team's **existing tests** — in any framework or
> language — into a fully functional `.syz` workspace, **capturing every meaningful detail
> without loss** and expressing it in current SYZYGY format.
>
> **The goal is losslessness, not perfection.** Don't over-engineer or chase an ideal output.
> The bar is: nothing in the tests is silently dropped — every case, assertion, input, setup,
> and outcome either lands in the workspace or is explicitly deferred/flagged with the user's
> agreement.
>
> **The centre of gravity is the Migration Document** (§4) — a single human-readable Markdown
> file that lists everything to be migrated, already segregated by which `.syz` component it
> belongs to. The user confirms and refines *that* document first; the workspace is built only
> from the confirmed document.
>
> **Fidelity is verified, not trusted.** The AI step is probabilistic — there is **no**
> determinism or zero-hallucination guarantee. Safety comes from user-confirmed understanding,
> gap→question (never guess), source-citation on every item, and a final `syz lint` gate.

---

## 0. Absolute rules (never violate)

1. **Capture without loss — anchored to the tests.** Every existing **test** — its cases,
   assertions, inputs, setup/preconditions, data, and expected outcomes — must appear in the
   Migration Document, mapped to a target or explicitly listed as deferred/skipped **with the
   user's agreement**. No silent omissions. Losslessness is measured against the **tests**, not
   "every behaviour in the codebase": supporting inputs (code, docs) only *clarify* the tests;
   they never expand scope beyond what the tests already cover.
2. **Ground strictly in the inputs.** Never invent endpoints, fields, payloads, status codes,
   assertions, or behaviour that is not present in an input or supplied by the user.
3. **Gap → question, never guess.** Any missing or ambiguous intent, mapping, or value → STOP
   and ask. More questions is better than a confident wrong answer.
4. **Speak the user's language.** Every question, the understanding, and the plan use
   **plain / domain terms**, never SYZYGY vocabulary. A first-time user must understand exactly
   what they are approving.
5. **Never hard-code SYZYGY standards.** SYZYGY's format, conventions, and test-design rules
   evolve. When you construct the workspace, **read the current `SYZ-GUIDELINES.md` and
   `SYZ-MANUAL.md`** (and the live schemas) as the authority for how to write every artifact —
   do not embed a fixed format from this file. This document governs the migration *process*;
   the SYZYGY *output format* always comes from the live docs. (See §6.)
6. **Unprocessable input → confirm skip or stop.** If any input can't be read or parsed for any
   reason, ask the user: skip this document, or halt the migration? Never proceed as if it were
   not there.
7. **Executor gate.** If an input needs a protocol SYZYGY can't execute yet, surface it up front
   and get a user decision before continuing (see §2c).
8. **The confirmed document is the contract.** The workspace is generated *only* from the
   user-confirmed Migration Document. Before generating, re-validate that the document is
   complete and correctly structured — guard against user or AI edits that moved detail out of
   place (see §5).

---

## 1. The pipeline (four phases, hard gates between)

```
Phase 0  Ingest & pre-flight → accept all inputs; extract; flag unprocessable (skip/stop);
   │                            existing-tests gate; executor-availability gate
Phase 1  Understand & draft  → build the Migration Document: every detail, segregated by
   │                            target .syz component, source-cited
Phase 2  Confirm & refine    → user confirms understanding; ask edits over MULTIPLE ROUNDS
   │                            and edit the doc until the user is fully satisfied
Phase 3  Construct & verify  → read the live syz guidelines/manual; build the .syz workspace
                                from the confirmed doc; syz lint; report lossless coverage
```

**Never skip a gate. Never construct the workspace before Phase 2 is fully confirmed.**

---

## 2. Phase 0 — Ingest & pre-flight

### 2.0. Existing-tests gate — check first, STOP if it fails

Before anything else, verify that **at least one existing test asset** is among the inputs — a
test suite/file in any framework or language, Postman test scripts, BDD/`.feature` specs, or
equivalent executable checks. If **none** is provided:

- **STOP.** Do not proceed. Tell the user plainly: *"I don't see any existing tests to migrate
  here. This flow converts tests you already have into SYZYGY format. If you want to create
  tests from your API specs or requirements instead, that's the standard authoring flow, not
  migration."*
- **Do not silently fall back** to authoring from specs/docs. Migration ≠ authoring.

Only once at least one existing test is confirmed does the rest of Phase 0 continue.

### 2a. Accept any text-bearing input

Ingest all provided inputs, regardless of format:

- **Source code** — any language.
- **Tests** — any framework/language.
- **API docs** — OpenAPI/Swagger, GraphQL SDL, WSDL/XSD, AsyncAPI, RAML, contracts.
- **Postman collections** (requests *and* test scripts), Insomnia, cURL, HAR.
- **Rich documents** — PDF, Word (`.docx`), PowerPoint (`.pptx`), spreadsheets.
- **Any other text-based docs** — Markdown, Confluence exports, plain text, tickets.

Extract the text/structure from each. For binary or rich documents (PDF/Word/PPT), extract the
readable content and preserve headings/tables/ordering where they carry meaning.

### 2b. Unprocessable input → ask

If an input can't be opened, parsed, or understood (corrupt, a scanned-image PDF with no text,
an unknown binary, encrypted), **stop and ask**: *"I couldn't read `<file>` (`<reason>`). Shall I
skip it, or would you like to stop so you can provide it differently?"* Record the decision.
Never silently ignore it.

### 2c. Executor availability gate — before drafting

Determine which integration protocols the inputs exercise (HTTP/REST, Kafka, MQ, SFTP/SSH,
SQL/NoSQL, key-value, gRPC, WebSocket, cloud object/queue/pub-sub, browser…). Treat
`SYZ-MANUAL.md` as the authority for **which protocols this SYZYGY version can actually run**.
If an input needs a protocol SYZYGY can't run yet, say so up front: *"Part of this talks to
Kafka, which this version of SYZYGY can't run yet. I can migrate the rest and record the Kafka
parts as deferred, or stop — which do you prefer?"* Get the decision, then proceed.

## 3. Input taxonomy — what maps to where

> **Existing tests are the spine — the primary source of what to migrate.** Their cases,
> assertions, setup, and expected outcomes define the scope. **All other inputs are supporting
> context**, used only to clarify or enrich the tests — never to add behaviour the tests do not
> cover. Placement heuristic: **behaviour/intent → requirements** (`PLUGIN-GUIDE` for one
> service, `DOMAIN` for a cross-service journey); **request details → a plugin's request
> surface**; **data → test data/examples**; **config → environments**. Always confirm the
> component-vs-E2E level with the user; classification is provisional until confirmed.

| Input | Role | Primary target(s) | Auto-extractable | Must ask |
|---|---|---|---|---|
| **Tests — any framework/language** (incl. BDD/`.feature` with steps) | **PRIMARY** | Component → `PLUGIN-GUIDE`; E2E → `DOMAIN` + split into plugins | Cases, assertions, inputs, setup/teardown, ordering, data | Which service each targets; E2E boundaries; hidden preconditions; unmappable assertions |
| **Postman test scripts** | **PRIMARY** | Requirements + assertions | Assertions as written | Confirm each is still intended; unparseable → ask |
| **Source code (any language)** | supporting | Clarify test intent; handlers → request surface | Endpoints, params, validation, error paths | Confirm inferred intent *against the tests*; never adds untested behaviour |
| **OpenAPI / GraphQL / WSDL / XSD / AsyncAPI / RAML** | supporting | Request surface + models for the *tested* operations | Operations, schemas, params, status codes, enums | Only for operations the tests exercise |
| **Postman / Insomnia / cURL / HAR (requests)** | supporting | Request surface for the tested calls | URLs, headers, bodies, params | Env values; intent per call |
| **Requirements / user stories / acceptance criteria (non-executable)** | supporting | Enrich requirement `notes` | Stated behaviour/rules | Map to the tests; don't expand beyond them |
| **PDF / Word / PPT / Confluence / text docs** | supporting | Domain knowledge in `notes` | Prose, tables, diagrams-as-text | Which parts clarify the tests |
| **Env configs (`.env`, Postman envs, config maps)** | config | `environments/*.yaml` | Names, URLs, non-secret config | Which are secrets (→ masked injection) |
| **Test data / fixtures (CSV/JSON/factories)** | data | `data.yaml` / outline `examples:` | Rows/values | Vary per case vs static; sensitive fields |
| **DB seeds / message samples / SFTP fixtures** | data (executor-dependent) | Data | Literal data | Needs a non-HTTP executor? (→ gate) |

### Cross-cutting mapping rules

- **One service → one `PLUGIN-GUIDE`.** **A cross-service journey → `DOMAIN`, split by system**
  (one plugin per participating system) — the split is not reliably inferable, so **ask the
  user to name and confirm the systems and their boundaries.**
- **Traceability:** every migrated item records its **source input** (filename + location) in
  the Migration Document, and every generated test links to the requirement it discharges.
- **Ambiguous level or classification → ask**, never default.

### Test-fidelity rules (the heart of migration)

- **Assertions.** Every assertion in a source test must map to a SYZYGY assertion **or be
  flagged as unmappable, with the reason** (e.g. custom code logic, snapshot comparison, UI/DOM
  check, DB-state inspection, non-deterministic value). Flagged assertions go to Open Questions
  / Deferred — **never silently dropped.**
- **Mocks / stubs are excluded — and disclosed.** Existing tests often mock external systems;
  SYZYGY executes for **real** against environments. **Do not migrate the mocks.** Migrate the
  real test steps the mock stood in for, and give the user **detailed, explicit notice of every
  mocked interaction that is therefore NOT covered** by the migrated tests, so the coverage
  boundary is unmistakable.
- **Out-of-scope tests.** A test with **no integration point** (pure unit/logic) has nothing to
  migrate — list it under Deferred / Not Migrating with the reason. A test whose integration
  point needs an **executor SYZYGY doesn't ship yet** → **hold** per the executor gate (§2c) and
  proceed on the user's decision.
- **Faithfulness mapping.** Maintain a **per-test map: original test → migrated scenario/case,
  assertion by assertion**, so the user can spot-check equivalence. `syz lint` proves
  syz-validity, **not** equivalence to the original — this map is how equivalence is checked.

## 4. The Migration Document (the central artifact)

While processing, produce **one Markdown file** (e.g. `MIGRATION-PLAN.md`) that captures
**everything to be migrated, pre-segregated by target `.syz` component.** This is what the user
reviews and confirms — not the raw inputs, and not the final YAML.

**Required structure (fixed sections, so nothing lands out of place):**

1. **Source Inventory** — every input, its detected type, and its status: `processed` /
   `skipped (user-approved, reason)` / `deferred (unsupported protocol)`.
2. **Domain & Journeys** *(→ `DOMAIN.yaml`)* — cross-service flows in plain language; for each:
   the systems it touches, the ordered steps, the rules, and success/failure outcomes.
3. **Per-Service Detail** *(→ each `PLUGIN-GUIDE.yaml`)* — one subsection per system:
   behaviours/requirements, inputs & constraints, business rules, error semantics — each in
   plain terms, each with its source citation.
4. **Test Cases & Flows** *(→ scenarios/outlines)* — the concrete cases to run: success,
   expected-failure, error, edge; which are parameterized and over what values.
5. **Test Data** *(→ `data.yaml` / `examples:`)* — the data, and which fields are
   sensitive/masked.
6. **Environments & Config** *(→ `environments/*.yaml`)* — hosts/URLs/config; which values are
   secrets.
7. **Test Mapping & Coverage Boundaries** — the per-test map (original test → migrated case,
   assertion by assertion) for spot-checking equivalence, **plus explicit disclosure of what is
   NOT covered**: every mocked interaction excluded, and any unmappable assertions.
8. **Deferred / Not Migrating** — unsupported protocols, out-of-scope (no-integration) tests,
   skipped inputs, and ambiguous items awaiting a decision. (This is the lossless ledger —
   anything not migrated is visible here, with a reason.)
9. **Open Questions** — everything still needing a user answer.

Every line item is written in **plain domain language** and tagged with its **source** and its
**target section**. Requirement IDs and SYZYGY-specific naming are added later, at construction
(§6), from the live guidelines — never invented here.

## 5. Phase 2 — Confirm & refine (multiple rounds)

1. Present the Migration Document and confirm the **understanding is correct** — in plain terms:
   *"Here's everything I found and where each piece will go. Is this right?"*
2. **Refine over multiple rounds — don't ask the user to rewrite the doc.** Ask targeted
   questions about what needs changing; *you* edit the document; re-present. Repeat until the
   user is **completely satisfied**.
3. **If the user edits manually**, validate that their edits keep the required structure (§4):
   the right section, the format intact. If something moved out of place or breaks the format,
   flag it and fix it with them.
4. **Before construction, re-validate the whole document:** all sections present, every item
   tagged with source + target, nothing landed in the wrong section, Open Questions empty, the
   Deferred list explicit. This guards against user/AI edits that displaced detail. The
   validated document is the **contract**.

---

## 6. Phase 3 — Construct & verify

1. **Read the live SYZYGY authority first** — the current `SYZ-GUIDELINES.md`, `SYZ-MANUAL.md`,
   and the active schemas in the workspace/dossier. These define how to write DOMAIN/
   PLUGIN-GUIDE requirements, scenarios, procedures, environments, IDs, and `covers:`. **Never
   hard-code these from memory or from this file** — they evolve; the live docs win.
2. **Scaffold the workspace** (`syz init`) and generate request surfaces from specs where
   available (`syz generate` from OpenAPI/Postman) to avoid re-deriving requests by hand.
3. **Build every artifact strictly from the confirmed Migration Document**, section by section:
   `DOMAIN.yaml`, each `PLUGIN-GUIDE.yaml`, scenarios/outlines, `data.yaml`,
   `environments/*.yaml`, plus all relevant SYZYGY docs. Cite each item's source.
4. **Run `syz lint`** and resolve every error and warning (schema, requirement IDs, `covers:`,
   dangling refs, coverage floor). Passing lint is the deterministic gate.
5. **Report lossless coverage** in plain terms, mirroring the Migration Document: what landed
   where, what's deferred, what's skipped — proving nothing was dropped silently.
6. **Hand off** a fully functional `.syz` workspace: how to run it (`syz run`), and what the user
   must still supply (secrets/env) before the first execution.

---

## 7. Losslessness & anti-hallucination checklist (before hand-off)

- [ ] Every input is accounted for: processed, skipped (user-approved), or deferred.
- [ ] Every meaningful detail from processed inputs appears in the Migration Document.
- [ ] Every migrated item traces to a source input; nothing invented.
- [ ] Every source assertion is mapped, or flagged unmappable **with a reason** — none dropped.
- [ ] Mocked interactions were excluded and **explicitly disclosed** as not covered.
- [ ] Out-of-scope (no-integration) tests are listed under Deferred with a reason.
- [ ] A per-test old→new mapping exists for the equivalence spot-check.
- [ ] Every ambiguity was asked, not assumed; Open Questions is empty.
- [ ] Classification and E2E system-splits were user-confirmed.
- [ ] Unsupported protocols were surfaced up front and resolved by a user decision.
- [ ] The workspace was written per the **live** SYZYGY guidelines/manual — no hard-coded format.
- [ ] `syz lint` passes clean.
- [ ] The coverage report matches the confirmed Migration Document; Deferred/Skipped is explicit.
