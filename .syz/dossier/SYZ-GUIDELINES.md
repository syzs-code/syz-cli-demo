# SYZYGY — Design Guidance & Best Practices

The *why* and the *how should I approach this*. For exact command/format reference see `SYZ-MANUAL.md`; for the test-authoring workflow see `SYZ-TESTING.md`.

## What is SYZYGY

**CLI to package, version and share integration knowledge — with agent-assisted test authoring and deterministic test execution.**

SYZYGY (SIZ-ih-jee) — the astronomical term for the perfect ALIGNment of celestial bodies — is an organisational testing unframework tool.

Every automation effort starts the same way: someone builds a test framework first. SYZYGY removes that step entirely. The structure, the organisation, the versioning — it is already done. You bring the knowledge of how your systems integrate; syz gives it a permanent, reusable home.

Its purpose mirrors its name: to align your organisation's integration knowledge into a single, durable form. Endpoints, payloads, sequencing, validation rules — encoded once into versioned plugins that every developer and stakeholder can reuse across any level of testing.

No more domain knowledge living only in someone's head. When an experienced member leaves, the integration knowledge stays.

The SYZ CLI is what makes this practical:

- **One tool, no infrastructure.** A single binary (`npm install -g syzs-cli`) — no servers, no databases, no central service. Runs on Linux, macOS, Windows, and any CI runner with Node.js.
- **Mocks or live systems — same scripts, same plugins.** Point them at a mock server during component testing, staging during integration, a production-like environment during UAT — just by switching the environment config. SYZYGY also supports plugins purpose-built for your internal mock services, so the abstraction stays consistent across every test phase.
- **Plugins are shared like any other code.** Versioned in git, installed via `syz install`, pinned in `dependency.json` — the same workflow your team already uses for libraries.
- **Everything is declarative YAML.** Scenarios, plugins, environments, assertions — open, diffable formats, reviewable in any code-review process. Your tests and knowledge are never trapped in a proprietary binary format.
- **Your vocabulary, not ours.** Test phase names (component, integration, e2e, UAT, or whatever your organisation calls them) are free-form — SYZYGY adopts your conventions.
- **AI where it earns its keep, deterministic everywhere else.** Plug in any OpenAI-compatible model (Anthropic, OpenAI, Azure, vLLM, or your own gateway) for the parts that genuinely benefit from reasoning — generating request payloads, evaluating semantic assertions, resolving dynamic inputs. The runtime, executors, and ledger stay fully deterministic, so results never drift because of model variability.
- **AI-assisted authoring, ready on day one.** Your AI coding assistant — Claude Code, Cursor, Copilot, Windsurf, Continue, Amazon Q, JetBrains AI, Gemini Code Assist, or Aider — already knows how to author SYZYGY tests. `syz init` lays down the right context file for each tool, so the framework rules and authoring guide are loaded the moment you open the project. No prompt engineering, no copy-pasting docs.
- **Every run fully traceable.** Each execution produces a structured ledger, a per-scenario debug log, and a clickable HTML report — answer "why did this pass or fail?" in seconds.

## Mental model

### Author roles

| Role | Writes | Typical source |
|---|---|---|
| **Scenario author** | `.syz/scenarios/**/*.yaml` | Any team member or AI assistant |
| **Plugin author** | `.syz/plugins/<name>/` | Domain team that owns the integration |

Plugins are usually acquired via `syz install` (shared from git) or `syz generate` (from an OpenAPI spec or Postman collection). Hand-authoring a plugin is for plugin owners creating new integrations from scratch.

### Procedure types — when to use which

| Type | Use when | Network call? |
|---|---|---|
| `send` | You want to call an API endpoint | Yes |
| `validate` | You want to assert on a prior response | No |
| `craft` | You want to build a local artifact (XML message, JSON payload, etc.) | No |
| `workflow` | You want to compose other procedures with input wiring and overrides | Depends on sub-procedures |

## Authoring patterns

**Cover the scope exhaustively by default.** When you author tests for a plugin, the default is *exhaustive within the scope of the request* — every send procedure in scope (plus any workflow that encodes a distinct functionality) earns ≥1 test or an explicit, surfaced deferral, opened with a coverage ledger — unless your team's `TEST-STRATEGY.md` coverage intent says otherwise. See `SYZ-TESTING.md` → *Cover the scope, exhaustively* for the floor definition and the four directives.

**Default all inputs from data.yaml (minimal scenario):**

Define defaults in the procedure YAML so scenarios only override what differs. Defaults seed the `{{ inputs.* }}` values the procedure's `http` block references:

```yaml
defaults:
  order: "{{ plugin.payments.data.send_order.body }}"
```

Then in a scenario: `inputs: {}` — all defaults apply. Override a single field:

```yaml
inputs:
  order:
    amount: 9999
```

**Workflow overrides for negative testing:**

Run the same workflow with a modified step input — no need to duplicate the full flow:

```yaml
- type: workflow
  procedure: payments.workflow_checkout
  overrides:
    - step: payments.send_order
      inputs:
        body:
          amount: 0
    - step: payments.validate_order_response
      inputs:
        expected_status: 400
```

**Parameterised outline for multiple cases:**

Use `examples:` to run one flow across multiple input rows — each row is a fully isolated execution with its own ledger and results folder:

```yaml
flow:
  - type: send
    procedure: payments.send_order
    inputs:
      amount: "{{ outline.amount }}"
      expected_status: "{{ outline.expected_status }}"

examples:
  - name: happy-path
    amount: 100
    expected_status: 201
  - name: rejected
    amount: 0
    expected_status: 400
```

**AI-generated test data in outlines:**

Example values can use `{{ ai: }}` to generate data at runtime:

```yaml
examples:
  - name: random-valid-order
    amount: "{{ ai: generate a random integer between 100 and 9999 }}"
    currency: "{{ ai: pick one of GBP, USD, EUR at random }}"
    expected_status: 201
```

**Cross-step ledger references:**

Wire the response of a send step into the next validate step:

```yaml
- type: send
  procedure: payments.send_order
  inputs: {}

- type: validate
  procedure: payments.validate_order_response
  inputs:
    response: "{{ ledger.payments.send_order.http.response }}"
    expected_status: 201
```

For a plain success gate — "the send completed with no transport/protocol error" — reach for the generated `<slug>_send_success` **workflow** first instead of hand-chaining the `send` + `validate_send_no_error` pair above; hand-chain only when a negative-path test asserts on the send's `body.error` itself (see `SYZ-TESTING.md` → *Author per the current contract*).

Use output shortcuts when available (shorter path, declared in manifest):

```yaml
inputs:
  orderId: "{{ ledger.payments.send_order.outputs.orderId }}"
```

### Direct ledger reference vs `ctx.var` — which to reach for

Both carry a value between steps. The default is a **direct `{{ ledger.<procedure>… }}` reference**: reach for it whenever the producing procedure and the response path are **known and local** — it is explicit and self-documenting about where the value came from.

Reach for **`{{ ctx.var.* }}`** (a `set:` block writes it; a later step reads it) only when a direct reference reads poorly:
- the value's **source is unknown or awkward at authoring time** (you don't want every consumer to hard-code one producer's response shape), or
- it is **shared across many steps or plugins**, or
- it must land in a place a ledger reference can't reach cleanly — the canonical case being a captured `id` threaded into a later URL **path** (`/orders/{{ ctx.var.order_id }}/items`). This is exactly what `syz generate` emits for path parameters.

Capture-and-reuse pattern:

```yaml
- type: send
  procedure: orders.create_order
  set:
    order_id: "{{ ledger.orders.create_order.http.response.fields.body.id }}"
- type: send
  procedure: orders.get_order        # procedure path: /orders/{{ ctx.var.order_id }}/items
```

**Masking a captured secret:** add the `ctx.var.<key>` to the step's `sensitive_fields`. It is masked **by location** — the ctx panel and every later injection site are blanked, at any length — while the live value still flows into later requests (long values are also value-net-registered as defence-in-depth). Think **location-first**: masking blanks the *field* a secret occupies (declared `sensitive_fields` + the framework's runtime-discovered injection/capture paths); the global substring value-net is a backstop for long values that leak into positions nothing tracked. It only holds values `>= 5` chars, so a short secret is masked by location, never by the value-net — which means the one case it can miss is a short value a server **echoes** into a field you neither injected nor declared. Remedy: declare that field in `sensitive_fields` (path-based, length-independent). Lint still flags a sub-floor (`< 5`-char) sensitive literal (`WEAK_SENSITIVE_CONTEXT_VAR`) as a nudge to consider that residual.

### Named `connections.<name>` handle vs identity in the procedure block — which to reach for

Two paths reach env-backed connection identity, and the default is the simpler one.

**Identity in the procedure's executor block (the default).** `syz generate` folds the location and auth identity straight into the procedure's `http:` block as `{{ env.<plugin>.<procedure>.<field> }}` references — one block, no `connection:` wrapper, no `lifecycle`. This is the right shape for the common case: a single send procedure with its own identity, a deployer overriding values through the env file. Hand-author the same way unless one of the reasons below applies.

Reach for a **named `connections.<name>` handle** (declared at env or scenario level, referenced by a step's `connection: <name>`) when:
- the **same identity is shared across several procedures or steps** and you want one place to define and override it;
- you need to **reuse or rename** the connection independently of the procedure (the procedure's executor block is the base identity any referenced name composes *over*, so a scenario handle can override just the `base_url` for one run);
- the executor is **stateful** (Kafka, a DB, SFTP…), where `connection:` is required and a `keep_alive` handle pools one live connection across steps. A generated stateful sample scenario already names a default `connection: send_<slug>` handle so pooling and teardown stay visible.

Precedence when both are present is always `step connection_overrides > scenario handle > procedure block > env handle` — the procedure block is the base layer, a scenario/step layer tunes or overrides it. Don't introduce a named handle just to "look organised"; the single-block default is less to read and less to get wrong.

### Waiting on async behaviour — `syz.wait` (fixed) vs `poll:` (until-converged)

Async and eventually-consistent integrations (a queue consumer catching up, an object appearing in a bucket, a downstream settling) tempt you to "wait a bit, then assert". **A fixed wait is a flakiness smell.** `syz.wait` blocks for a *guessed* duration: too short and the test flaps on a slow run; too long and every run pays the worst case. It encodes a timing assumption, not a contract.

- **Reach for `poll:`** (a bounded retry-until-converged modifier on a `workflow` step — see `SYZ-MANUAL.md`) whenever you are waiting **for the system to reach a state**. It re-runs the workflow until its validate passes (early-exit) or a bound trips, so it is as fast as the system allows and as patient as the bound permits — the right primitive for eventual consistency.
- **Reach for `syz.wait`** only for a **genuinely fixed window** that is part of the contract, not a guess: a rate-limit window you must let lapse, a TTL/cache expiry, a token that becomes valid at +N seconds, a job scheduled for a known delay. Here the duration *is* the thing under test.

If you find yourself tuning a `syz.wait` `ms` value up because the test flakes, that is the signal to convert it to a `poll:`.

## Capturing knowledge — `DOMAIN.yaml` & `PLUGIN-GUIDE.yaml`

The knowledge layer is **AI-authored from a natural-language conversation**, then lint-validated like a scenario. The schema (full reference in `SYZ-MANUAL.md`) exists so the AI **picks field names from a known menu instead of inventing one each session** — consistency across models and sessions is structural, not a matter of discipline. A few principles:

- **Domain language only — no syz vocabulary.** These files describe *what the application does* in the user's terms. Never mention executors, procedures, scenarios, send/validate, `covers:`, or test techniques here. They never restate `plugin.yaml` / procedure manifests / input models, and carry no plugin name or version (folder = name, `plugin.yaml` = version).
- **Author before procedures exist.** A requirement is captured as the team understands the system — typically *before* any plugin or procedure is generated. The requirement→procedure binding is resolved only later, at scenario-authoring time, via `covers:`. Do not wait for generation to write requirements.
- **Mark drafts in-progress with a leading `_`.** Because requirements are captured before their tests exist, a fresh one would otherwise read as an *uncovered* gap. Prefix its id with `_` (`_REQ-…`) while you are still shaping it: it is excluded from the coverage floor and from `syz rtm` (so it is never mistaken for a gap), yet still fully validated. Remove the `_` the moment it is ready to be tested — the `_` is a status marker, not part of the id, so promoting it breaks nothing. Don't leave requirements in-progress indefinitely; the marker is for work you intend to finish, not a way to silence real gaps.
- **Concrete, never abstract.** Capture real constraints (a range, a value set, an error code, a legal transition). There is deliberately no `invariants` field — abstract invariants are a hallucination magnet. If you cannot make it concrete, it does not belong.
- **Write rich `notes:` — humans depend on them.** There is no rendered view of these files; humans read the YAML directly, and `notes:` is the human-facing narrative. It is mandatory on every requirement. Write enough that a reader understands the requirement without any tooling — a terse `notes:` defeats the layer's reason for existing.

**Writing a good `behaviour` block.** Think Given/When/Then, but disciplined:

- **`given`** — the existing context and state the requirement assumes (a valid card; a placed order; an empty cart). Preconditions live here (or in the `preconditions` field), never as an `and`/`assume` keyword.
- **`when`** — the **single** action under test. One `when` = one trigger. If you need two actions, you have two requirements (or a DOM `flow`).
- **`then`** — the observable outcomes. Use a **list** when there are several (`then: [payment settles, fulfilment begins, the customer is notified]`) — a list is the implicit "and".

Each of the three may be a single string or a list of strings; reach for a list only when there are genuinely multiple clauses.

**Maintaining the `areas:` registry (DOMAIN.yaml).** A DOM requirement's scope must be a declared `areas[].key`. The registry is **self-bootstrapping and AI-maintained — no manual curation**. Before adding requirements: (1) read the existing files and run `syz rtm` to learn what is already covered, so you do not duplicate a requirement or a test; (2) **reuse** an existing `areas[].key` wherever it fits — append a new `{key, title, description}` only when none does; (3) match the established format and style — the existing corpus is the style guide. `syz lint`'s `UNKNOWN_DOMAIN_AREA` forces you to register any new area in the same change, so the registry can never silently fall out of sync — and `UNUSED_DOMAIN_AREA` (warning) closes the other direction, flagging a registered area nothing was ever bound to.

**Which lint mode to reach for.** `syz lint` requires exactly one of `--env <name>` or `--knowledge`, and infers neither — a missing flag is an error rather than a quiet downgrade, so a typo in CI can never turn a full pre-flight into a partial check that still exits 0. Choose by what you are working on, not by habit:

- **While capturing or editing requirements** — `syz lint --knowledge`. It validates `DOMAIN.yaml` + every `PLUGIN-GUIDE.yaml` and reads no environment, scenarios, or procedures, so it works from the very first requirement, before an endpoint or environment exists. Use it as the tight write → lint → fix loop during a requirements interview. Add `--plugin <name>` when several people are authoring different guides in parallel.
- **Before running anything** — `syz lint --env <name>`. This is the real pre-flight and the one that belongs in CI: it checks everything knowledge mode checks **plus** scenarios, procedures, plugins, and the environment. Knowledge mode is a faster inner loop, never a substitute for it.

The one behavioural difference is coverage: knowledge mode suppresses `UNCOVERED_REQUIREMENT` (with nothing authored yet it would fire on every requirement and bury the real findings) and reports a census line instead. Every shape rule — ids, layer/scope, duplicates, schema — runs identically in both, so a draft validated in knowledge mode never rots.

**The L2 / L3 litmus** (the same rule as `DOMAIN.yaml` vs `PLUGIN-GUIDE.yaml`): is this true about **one** integration (→ that plugin's `PLUGIN-GUIDE.yaml`, a `-PG-` id) or about how the business **stitches integrations together** (→ `DOMAIN.yaml`, a `-DOM-` id)? `syz lint` enforces it — a `-PG-` id may only live in a plugin guide, a `-DOM-` id only in `DOMAIN.yaml`.

### `guidelines:` — binding authoring rules (the HOW), distinct from requirements (the WHAT)

Both `PLUGIN-GUIDE.yaml` and `DOMAIN.yaml` may carry a `guidelines:` list alongside `requirements:`. A **guideline** is a rule the author must **obey when constructing** a procedure/scenario or choosing/configuring an executor — the **HOW** — as opposed to a requirement, which is a behaviour the tests **verify** — the **WHAT**. Format reference is in `SYZ-MANUAL.md`; the decisions that matter here:

- **When to record one.** You made (or discovered) a construction rule that is **not a business behaviour** and is **not tested** — most often forced by a *technology change*: a framework upgrade that adds a required header, an OS/security patch that mandates TLS 1.3 or mutual auth, a vendor deprecating a transport so only one executor is valid. It changes *how you must talk to the integration*, while the behaviour under test is unchanged. If instead the integration's observable behaviour/contract changed, that is a **requirement**, not a guideline — even when a tech upgrade caused it. Sort by **effect**, not by cause.
- **Guidelines may name mechanics — requirements may not.** Requirements are pure domain language (no syz/executor/procedure vocabulary). Guidelines are the deliberate exception: a guideline *should* name executors, headers, TLS, and settings, because steering the mechanics is its entire job.
- **Obeyed, never tested.** A guideline carries **no `covers:`** and never appears in `syz rtm`. Apply it while authoring and leave a `# see GL-<id>` comment where you implement it; do not write a test "for" a guideline.
- **git owns the history.** A guideline states what is true *now*. When a platform moves on, edit or delete the entry — git and the plugin version are the change log; do not keep an in-file changelog of superseded rules.
- **This section vs SYZ-GUIDELINES.md — one concept, layered by scope.** `SYZ-GUIDELINES.md` (this document) holds **framework-wide** authoring standards that apply to every project. A `guidelines:` list in `PLUGIN-GUIDE.yaml` holds **plugin-specific** rules; one in `DOMAIN.yaml` holds **domain-wide** rules for this workspace. Same idea — "rules the author follows" — narrowing from framework → domain → plugin. All apply together.

## General test case design techniques

Coverage *breadth* (every send procedure in scope gets a test — see `SYZ-TESTING.md` → *Cover the scope, exhaustively*) is only half the job. *Depth* is how thoroughly each unit is exercised. Test like a world-class tester: for each unit under test, reach for the techniques **relevant to its shape** — never a single happy-path assertion where classes, boundaries, and error paths went untested, and never the whole catalogue applied blindly to every field. Each technique below names a **relevance signal** ("reach for it when…") and points at the syz primitive that expresses it — the YAML lives once in *Authoring patterns* above, not here.

**Input-driven — one operation, vary its inputs:**

- **Equivalence partitioning** — divide an input into classes that should behave alike and test one representative per class. *Reach for it when* a field has distinct input classes (valid vs invalid, role types, currency codes, account states). *Primitive:* one `examples:` outline row per class (*Parameterised outline*).
- **Boundary-value analysis** — test at and just across each limit: min, min−1, max, max+1, empty, length cap, zero. *Reach for it when* a field is bounded (numeric range, string length, page size, quantity). *Primitive:* an `examples:` row per boundary; `{{ ai: }}` to synthesise edge values.
- **Decision-table** — enumerate the combinations of conditions and their expected outcome. *Reach for it when* output follows a rules matrix (discount = f(tier, amount, coupon)). *Primitive:* one `examples:` row — or one workflow `overrides` row — per rule.
- **Pairwise / combinatorial** — when full combinations explode, cover every *pair* of parameter values instead of every tuple. *Reach for it when* several independent parameters interact and exhaustive rows are infeasible. *Primitive:* a reduced `examples:` set chosen for pairwise coverage.
- **Error-guessing / negative** — deliberately feed malformed, missing, or hostile input and assert the contract's failure behaviour. *Reach for it for* every operation that can reject input (validation errors, 4xx, a populated `body.error`). *Primitive:* a workflow `overrides` row flipping one input plus a validate asserting the error — this is exactly the `body.error` carve-out where the hand-chained `send` + bespoke validate is correct (`SYZ-TESTING.md`).

**Flow / stateful — drive a sequence, assert the journey:**

- **State-transition** — move the resource through its lifecycle and assert each legal transition (and that illegal ones are refused). *Reach for it when* the integration has ordered states (created → paid → shipped → cancelled). *Primitive:* a `ctx.var` capture-reuse chain across send steps (*Direct ledger reference vs `ctx.var`*).
- **User-flow / scenario** — exercise a realistic multi-step journey end-to-end rather than isolated calls. *Reach for it when* the business value lives in a sequence (checkout; onboarding; acquire-token → create → verify → delete). *Primitive:* a `workflow` procedure composing the steps, or a multi-step scenario `flow`.

**Selecting techniques — relevance-driven, never blind, layered with `TEST-STRATEGY.md`.** Read `TEST-STRATEGY.md` first. The effective guidance is the **union** of this catalogue and any intent your team recorded there: this catalogue is the working baseline, `TEST-STRATEGY.md` *layers on top* — adding emphasis, required boundaries, or a rigor cap — and wins **only on the specific points where it directly contradicts** the default (e.g. "component is smoke-only — skip BVA there"). Absent a contradiction, both apply (the same field-by-field layering as connection/executor-config precedence). With `TEST-STRATEGY.md` left an empty stub — the common case — this catalogue alone is the **self-sufficient default**: match each technique's relevance signal to the actual shape of the unit under test, **proportional to the scope the user requested** (M44C). Boundary *values* themselves are domain knowledge — find them in the plugin's `PLUGIN-GUIDE.yaml` / `data.yaml`, not here — so the same techniques apply equally to HTTP fields, Kafka messages, SQL params, or object-store keys.

## Selecting what to run — tag vs manifest playlist

`--tag` and a suite manifest both narrow a run, but they answer different questions (full syntax in `SYZ-MANUAL.md` → *Selecting a subset*).

- **Tag when the grouping is a property of the scenario** that you will slice by repeatedly and dynamically: `smoke`, `critical`, `@payments`, `slow`. Tags live next to the test, travel with it, and combine across files — `--tag smoke` finds every smoke row wherever it lives. Put the broad label on the scenario (`tags:` at the top), and only refine a single outline row with a row-level `tags:` when one example deserves its own slice (e.g. one `edge` case among standard rows). Keep the vocabulary small and shared — a tag only helps if more than one scenario uses it.
- **Curate a manifest when the grouping is an explicit, ordered, named list** that you want to commit and review as one artifact: a release gate, a regression pack, a demo path. A manifest is a file under `.syz/suites/`, so it is version-controlled, diff-able, and orders its entries deliberately — use it when *which* scenarios and *in what order* is itself the decision. Folder entries keep it terse (`integration/` pulls the whole tree); list individual files when the order or selection matters.
- **They compose.** A manifest defines the candidate set; `--tag` / `--example` narrow within it. `syz run --suite .syz/suites/release.suite.yaml --tag smoke` runs the smoke rows *of the release set*. Use `syz lint` with the same flags first — it previews the exact rows the run will execute, so a typo'd tag or example surfaces before you spend a run.

## Choosing the right operator

- **`equals` / `contains` / `matches`** — the default choice. Deterministic, fast, no API cost. Use whenever the expected value can be expressed as a literal, substring, or regex.
- **`expression`** — reach for this when you need boolean logic across multiple fields of the same response (e.g. total must equal subtotal plus tax). The expression has access to `response` and `inputs` and must return a boolean.
- **`operator: ai`** — use for rules that are genuinely semantic or non-deterministic: time-based routing, "the message sounds like a success", formatting conventions a regex cannot capture. Do not use `ai` for anything expressible deterministically — AI assertions add latency, consume API quota, and can produce inconsistent results under the same inputs.

(The full operator table and its applicable types live in `SYZ-MANUAL.md` → *All assertion operators*.)

  run: npm install -g syzs-cli

  run: syz lint --env ci
- name: Run tests

For a fast pre-merge gate, run a tagged subset (`syz run --suite .syz/scenarios/ --env ci --tag smoke`) on every PR and the full suite (or a `.syz/suites/release.suite.yaml` manifest) on the protected branch.

## Login once, reuse the token

A send procedure POSTs to `/login` and declares an output shortcut in its manifest:

```yaml
outputs:
  token:
    path: "$.fields.body.token"
    description: "Bearer token for subsequent requests"
```

Downstream procedures then read the token from the ledger:

```yaml
inputs:
  Authorization: "Bearer {{ ledger.<plugin>.send_login.outputs.token }}"
```

This pattern works in scenario `flow` steps, workflow wiring, and procedure `defaults`. The token is resolved once when the login step runs and is available to all subsequent steps in the same execution.
