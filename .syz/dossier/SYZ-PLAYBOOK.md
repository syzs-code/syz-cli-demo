# SYZYGY — Playbook (what does the user want?)

This document is for the **AI agent working with a human** in this workspace. The human may be a business analyst, product owner, subject-matter expert, tester, or developer — **assume no syz knowledge**. Your job: figure out what they want, run the right activity below, and keep them informed in plain language.

**The working stance — the agent operates, the human answers:**

- **You run the `syz` commands; the human supplies knowledge and decisions.** Never tell a user to "run `syz lint`" — run it yourself and explain the result.
- **Narrate in plain terms** what was done, what is being done, and what will happen next. Avoid syz vocabulary (plugin, scenario, procedure, lint) unless the user uses it first — say "the folder that records what the system should do", "the test", "the check". Scale terminology up only when the user demonstrates fluency.
- **When any specific is unknown — which integration, which environment, which test — ask the user. Never guess, and never go hunting.** The binding interaction contract in `SYZ-INDEX.md` applies at all times: knowledge lives only inside `.syz/`, unless the user explicitly points elsewhere.

## Which activity? — intent triage

The user's words will be plain language, not these exact phrases — match the *intent*. When no row fits, or two could, **ask the user which they mean**, offering the activities by their plain descriptions.

| The user wants to… | Activity | Do this |
|---|---|---|
| "note down / record what the system should do", "capture requirements", "document how X behaves" | **Record requirements** | Playbook 1 below |
| "why did my test fail?", "something is red", "what went wrong?" | **Investigate a result** | Playbook 2 below |
| "run the tests", "check the system", "test it against staging" | **Run tests** | Playbook 3 below |
| "what is this folder?", "what is syz?", "where do I start?" | **Get oriented** | Playbook 4 below |
| "teach me syz", "walk me through it hands-on", "show me by doing", "give me a hands-on refresher" | **Teach me hands-on** | Playbook 5 below |
| "write / add a test", "cover this behaviour with a test" | **Author a test** | Read `SYZ-TESTING.md` and follow its authoring workflow — the knowledge recorded via Playbook 1 is its input |
| "bring our existing tests into syz" (tests already exist in another tool or framework) | **Migrate existing tests** | Read `SYZ-MIGRATE.md` **if-and-only-if** the task is migrating existing tests — never for authoring net-new tests |
| "what does this field / flag / error code mean?" | **Look something up** | Read `SYZ-MANUAL.md` (the reference) and answer from it — never from memory |

## Playbook 1 — Record requirements

Capture what a system *should do* — in the user's own words — so it becomes durable, checkable team knowledge. No endpoint, spec, or test has to exist first.

1. **Identify the integration — by asking, never by searching.** List the folders under `.syz/plugins/` and `.syz/plugins.installed/` and offer them by name: "Is this about one of these, or something new?"
2. **If it is new, create its knowledge shell:** run `syz generate plugin --name <name> --guide-only`. Tell the user: "I've created a place to record how <name> should behave — nothing needs to be built or connected yet."
3. **Interview the user, one focused question at a time, in their domain language.** Cover, area by area: what the integration is for; the normal successful flow; the inputs and their constraints; what must never happen and how errors should behave; the edge cases they worry about. Reflect back what you heard before recording it.
4. **Record each agreed behaviour as a requirement** in that integration's `PLUGIN-GUIDE.yaml` (`requirements:`, id `REQ-<PLUGIN>-PG-<NNN>`; a behaviour still being discussed gets the in-progress marker `_REQ-…`). Knowledge that spans several integrations belongs in `dossier/DOMAIN.yaml` instead (register its area in `areas:`). Exact schema and field menu: `SYZ-MANUAL.md`.
5. **Validate:** run `syz lint --knowledge` yourself and fix any issue it names, until clean. This is the mode built for exactly this moment — it checks `DOMAIN.yaml` + every `PLUGIN-GUIDE.yaml` and reads **no** environment, scenarios, or procedures, so it works before any of those exist and never asks the user for an environment file that is not theirs to author. It raises no "uncovered requirement" nag either — that is expected at this stage. Then tell the user, plainly: "Everything we recorded is well-formed and saved." Two warnings worth acting on while you are here: `PLACEHOLDER_KNOWLEDGE_CONTENT` means a requirement's `notes:` is still the scaffold example (go back and write the real narrative with the user), and `UNUSED_DOMAIN_AREA` means an area was registered but nothing was bound to it.
6. **Show where things stand:** run `syz rtm` and explain which recorded behaviours already have tests and which do not yet — uncovered is normal and expected at this stage; tests come later (see the triage row *Author a test*).

## Playbook 2 — Investigate a result

1. **Locate the run:** the latest folder under `.syz/results/` — or, if the user wants a fresh look, re-run via Playbook 3 (including its confirmation step).
2. **Classify before diving in.** Each step reports one outcome — explain it in these plain terms first: **failure** = the system did not behave as the test expects; **error** = the test could not run (something is miswired or missing); **exception** = something broke unexpectedly mid-run; **aborted** = the run stopped before this step finished.
3. **Walk the evidence, plainest first:** `index.html` (the human-readable report), `ledger.json` (the structured record of every step — what was sent, what came back), `debug.log` (the phase-by-phase trace).
4. **For a failure — the *test* may be right and the *system* wrong.** Read the requirement the test covers (its `covers:` ids point into `PLUGIN-GUIDE.yaml` / `DOMAIN.yaml`), compare it with what actually happened, and present both to the user: "The recorded behaviour says X; the system did Y — which is correct?" Never "fix" the test before the user answers.
5. **For an error or exception:** look up the printed error code in `SYZ-MANUAL.md`'s error reference, fix the named cause, and re-run just the affected test (Playbook 3, narrowed).
6. **Close the loop in plain language:** what happened, what was changed, what happens next.

## Playbook 3 — Run tests

1. **Confirm the target environment:** list `.syz/environments/` and ask which one. If none exists, create it with the user — they supply the addresses and credential names; secrets stay as `{{ os-env-var:NAME }}` references, never literal values (format: `SYZ-MANUAL.md`).
2. **Before running against a shared or live system, say so and get the user's explicit OK** — these tests make real calls to real systems (`SYZ-NOTICE.md`).
3. **Scope the run:** everything, or a slice (`--tag`, `--example`, or a saved suite playlist) — see *Selecting a subset* in `SYZ-MANUAL.md`.
4. **Run it yourself** — `syz run --suite .syz/scenarios/ --env <name>` — and narrate the summary in plain terms: how many checks ran, how many passed, what is red.
5. **Offer the report** (`index.html`) and, for anything red, continue with Playbook 2.

## Playbook 4 — Get oriented

1. **Two-sentence orientation:** "This `.syz` folder holds your team's integration knowledge and its tests — what your systems should do, recorded in plain terms, and the tests that prove they do it. syz is the tool that keeps that organised and runs the tests the same way every time."
2. **For the full picture,** read *What is SYZYGY* and the mental model in `SYZ-GUIDELINES.md` and summarise it plainly — do not paste it.
3. **Show what already exists here:** the integrations recorded (`.syz/plugins/`, `.syz/plugins.installed/`), the tests (`.syz/scenarios/`), the environments (`.syz/environments/`) — and, if requirements exist, what `syz rtm` says about coverage.
4. **Ask what they would like to do first** and jump to that row of the triage table.

## Playbook 5 — Teach me hands-on

Use this when the user wants to **learn syz by doing** — a guided, hands-on walkthrough — or wants a hands-on refresher. This is the **one and only** route to `SYZ-TUTORIAL.md`; the default authoring/running routes never open it. (Playbook 4 above is the *conceptual* "what is syz?" orientation to `SYZ-GUIDELINES.md`; this playbook is the *hands-on* path.)

`SYZ-TUTORIAL.md` is written in human-imperative voice ("Step 1: *you* install Node.js"). You are **teaching from it**, not operating from it — so adapt it to the person in front of you rather than reciting it.

1. **Open `SYZ-TUTORIAL.md` and teach it section by section**, in order. It is a self-contained linear path — install → `syz init` → capture → generate → author → run → read results — so follow its sequence; do not jump ahead.
2. **Adapt terminology to the user's level** (agent-operates/human-answers, as always): for a non-developer, narrate each section in plain terms and let them do the hands-on steps at their pace; for a fluent user wanting a refresher, move faster and use syz vocabulary directly.
3. **Pause at the end of each section**, check understanding, and answer questions before moving on. Let the user set the pace — a walkthrough is theirs to drive.
4. **When a section raises a "how exactly?" question** the tutorial's optional "go deeper" pointers cannot settle, look the specifics up in `SYZ-MANUAL.md` yourself and answer plainly — never send the user off to read the reference.
5. **When the walkthrough is done**, return to the triage table and ask what they would like to do for real first (record requirements, author a test, run tests).
